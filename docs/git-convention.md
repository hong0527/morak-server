# Git 컨벤션

## 브랜치

`main`은 항상 실행되는 상태를 유지합니다. **main에 직접 커밋하지 않습니다.**
모든 작업은 브랜치를 따서 하고 PR로 합칩니다.

```
main
 ├── feat/member-signup
 ├── feat/match-request
 └── fix/proof-duplicate-check
```

브랜치 이름은 `타입/작업내용` 형태로 짓습니다. 영문 소문자와 하이픈만 씁니다.
이슈 번호를 쓰지 않으므로, 브랜치 이름 자체가 그 작업의 식별자입니다.

브랜치는 **3일 안에** main으로 돌아오는 크기로 자릅니다.
3일이 넘어가면 작업이 너무 큰 것이므로, 되는 데까지 잘라서 먼저 PR을 올립니다.
브랜치가 길어질수록 충돌이 커지고, 커진 충돌은 해결하다 실수가 납니다.

### 작업 시작

```bash
git switch main
git pull origin main
git switch -c feat/member-signup
```

main에서 최신을 받고 브랜치를 따는 순서를 지켜야 충돌이 줄어듭니다.

PR이 머지되면 브랜치는 지웁니다. 레포 설정에서 자동 삭제를 켜두면 신경 쓸 필요가 없습니다.

## 커밋

### 타입

브랜치와 커밋이 같은 목록을 씁니다.

| 타입 | 쓰는 경우 |
| --- | --- |
| `feat` | 새 기능 |
| `fix` | 버그 수정 |
| `refactor` | 동작은 그대로, 구조만 변경 |
| `docs` | 문서만 변경 |
| `test` | 테스트 추가·수정 |
| `chore` | 빌드 설정, 의존성, 그 밖의 잡무 |

이 6개만 씁니다. `style`, `perf`, `ci`, `build`는 쓰지 않습니다.
애매하면 `chore`로 보냅니다. 타입을 고르느라 멈추는 게 더 손해입니다.

제목은 한국어로 씁니다. 타입 키워드만 영어입니다.
팀 전원이 한국어를 쓰는데 영어로 옮기면 메시지가 짧고 부정확해집니다.

### 형식

```
타입: 제목

본문 (필요할 때만)
```

- 제목은 50자 안쪽, 마침표를 찍지 않습니다.
- 제목은 "무엇을 했는지"를 씁니다. `추가`, `수정`, `삭제` 처럼 끝냅니다.
- 본문은 "왜 그렇게 했는지"를 씁니다. 코드를 보면 아는 내용은 적지 않습니다.
- 이모지를 쓰지 않습니다.

### 예시

```
feat: 카카오 로그인 API 추가
```

```
fix: 같은 날 인증이 두 번 등록되던 문제 수정

daily_slot 생성 컬럼이 BLOCKED 상태까지 포함하고 있어
검열에 걸린 사진 때문에 그날 재업로드가 막혔다.
APPROVED와 PENDING_REVIEW만 슬롯을 차지하도록 조건을 좁혔다.
```

```
refactor: 매칭 잠금 로직을 MatchLockRepository로 분리
```

### 커밋 단위

한 커밋은 한 가지 일만 합니다. 되돌릴 때 그 커밋만 지우면 되는 크기가 기준입니다.

- 기능 추가와 리팩터링을 한 커밋에 섞지 않습니다.
- 포매팅만 바꾼 변경은 따로 커밋합니다. 섞이면 리뷰할 때 실제 변경이 묻힙니다.
- 반대로 너무 잘게 쪼개도 히스토리를 읽기 어렵습니다.
  "엔티티 추가 → Repository 추가 → Service 추가"는 기능 하나로 묶는 편이 낫습니다.

Squash and merge를 쓰므로 작업 중의 커밋은 main에 남지 않습니다.
그래도 커밋을 나누는 이유는, 리뷰어가 커밋 단위로 diff를 읽고
작업 중에 특정 지점으로 되돌아갈 수 있어야 하기 때문입니다.

### 커밋하기 전에

```bash
git status
git diff
```

의도하지 않은 파일이 딸려 들어가지 않았는지 봅니다.
`.env`, `application-local.yml`, 로컬 업로드 파일은 `.gitignore`에 있지만 한 번 더 확인합니다.

## Pull Request

### 언제 올리나

작업 브랜치의 기능이 동작하는 시점에 올립니다.

크기는 **변경 300줄 안쪽 / 파일 10개 안쪽**을 기준으로 합니다.

이 숫자는 감이 아닙니다. Cisco 사내 코드리뷰 연구(2,500건, 320만 줄)에서
한 번에 200~400줄을 넘기면 결함 발견률이 떨어졌고, Google 사내 데이터에서는
변경의 약 90%가 10파일 미만이었습니다.

넘어갈 것 같으면 PR을 쪼갭니다. 쪼개는 순서 예:

1. 엔티티
2. Repository + Service
3. Controller + DTO

대량 포매팅이나 자동 생성 코드는 줄 수에서 빼되, 별도 PR로 분리합니다.

### 제목

커밋 제목과 같은 형식을 씁니다. Squash and merge를 쓰면
**PR 제목이 main의 커밋 제목이 되므로** 커밋 메시지처럼 씁니다.

```
feat: 회원가입과 로그인 API 구현
```

### 본문

이 프로젝트는 이슈를 쓰지 않으므로, PR 본문에 필요한 맥락을 다 담습니다.
`.github/PULL_REQUEST_TEMPLATE.md`가 있어서 PR을 열면 양식이 자동으로 채워집니다.

"확인 방법"에는 리뷰어가 그대로 복사해 실행할 수 있는 명령어를 적습니다.
이게 있으면 리뷰가 코드 읽기에서 동작 확인으로 바뀝니다.

### 머지

- 리뷰어가 있으면 승인 후 머지합니다.
- 리뷰어가 없는 작업(백엔드 단독 작업 등)은 셀프 머지합니다.
  대신 머지 전에 PR의 **Files changed** 탭을 처음부터 끝까지 한 번 읽습니다.
  로컬에서 보던 diff와 다르게 보여서, 여기서 눈에 띄는 게 실제로 있습니다.
- **CI가 초록불이 아니면 머지하지 않습니다.** 이게 승인을 대신하는 게이트입니다.
- 머지 방식은 **Squash and merge**를 씁니다. 작업 중의 자잘한 커밋이 main에 남지 않습니다.
- 머지 후 브랜치를 삭제합니다.

### 리뷰

- 하루 안에 봅니다. 리뷰가 밀리면 브랜치가 길어지고 충돌이 커집니다.
- 고쳐야 하는 것과 취향인 것을 구분해서 말합니다.
  취향인 의견은 "이건 제안인데" 하고 시작하면 서로 편합니다.

## 프론트엔드와 협업

API가 바뀌면 **코드보다 명세를 먼저 고치고 공유**합니다.
[docs/api-spec.md](api-spec.md)가 계약이고, 프론트는 이 문서를 보고 작업합니다.

- 응답 필드를 추가하는 건 언제든 괜찮습니다.
- 필드 이름을 바꾸거나 없애는 건 프론트에 먼저 알리고 합의한 뒤에 합니다.
- 에러 코드를 새로 만들면 명세의 에러 코드 표에도 같이 추가합니다.

명세를 고치는 PR은 코드 PR과 분리해서 먼저 올리면 서로 기다리는 시간이 줄어듭니다.

### 배포 순서

배포 시점을 억지로 맞추지 않습니다. 맞추려 하면 서로 기다리게 됩니다.
대신 API를 하위 호환으로 유지해서 순서에 상관없이 배포되게 만듭니다.

순서를 맞춰야 하는 변경이라면 **백엔드를 먼저 배포**합니다.
새 응답 필드는 프론트가 무시하면 그만이지만, 반대는 깨집니다.

필드를 없애야 할 때는 한 번에 하지 않고 세 단계로 나눕니다.

1. 새 필드를 추가하고, 구 필드도 그대로 둔 채 백엔드 배포
2. 프론트가 새 필드로 전환하고 배포
3. 구 필드를 제거하고 백엔드 배포

### 레포 간 참조

PR 본문에서 다른 레포의 PR을 `소유자/레포#번호` 형태로 적으면 링크가 걸립니다.

```
관련: hong0527/morak-client#42
```

다른 레포의 이슈는 `Closes`로 자동 종료되지 않습니다. 링크만 걸립니다.

## 충돌이 났을 때

```bash
git switch main
git pull origin main
git switch feat/my-work
git merge main
```

충돌 파일을 고치고 커밋합니다.

`git rebase`는 **다른 사람이 체크아웃한 브랜치**에서 쓰지 않습니다. 그쪽 히스토리가 깨집니다.
혼자 쓰는 작업 브랜치라면 push한 뒤에도 rebase해도 됩니다.
그때는 `git push --force-with-lease`를 씁니다. 그냥 `--force`는 쓰지 않습니다.
`--force-with-lease`는 원격이 내가 아는 상태와 다르면 거부해서, 남의 작업을 덮어쓰는 사고를 막습니다.

## 하지 말아야 할 것

- main에 직접 push
- main으로의 force push (예외 없음)
- 공유 중인 브랜치로의 force push (혼자 쓰는 브랜치는 `--force-with-lease`로 가능)
- 커밋 메시지에 `수정`, `ㅇㅇ`, `asdf` 같은 내용 없는 제목
- 빌드가 깨진 상태로 PR

# 원문 대비 변경 사항 — 팀 승인 요청 (2026-08-12)

> **왜 이 문서가 필요한가**: 최종 검증(원천 대조 축)에서 밝혀진 사실 — 현재 설계 정본은 "팀이 준 요구를 정리한 것"이 아니라 **"팀 요구 + 화수·클로드의 판단을 병합한 것"**이고, 병합 사실이 일부만 표기되어 있었다. 아래 6건은 **원문이 명시적으로 A라고 쓴 것을 B로 바꾼 것**이며, 팀 승인 없이 진행하면 안 된다.
> 기준선: `원천자료_기능명세서_원문.md` / 현재 설계: `API명세서_모락_v1.0.md` 외 3종.

## 승인 요청 6건

### 1. 프로필 이미지·SNS 닉네임 저장 → **미저장**

| | |
|---|---|
| **원문** | 요구1-1 데이터: "SNS 제공자 식별자, **프로필 이미지, 닉네임**, (제공 시) 생년월일을 저장한다" / 요구6-3: "SNS 식별자·검증 생년월일·**프로필**을 자동 삭제" |
| **변경** | SNS 닉네임·프로필 이미지를 **저장하지 않고**, 가입 시 서버가 `익명 {동물명}{2자리}`를 생성해 쓴다 |
| **이유** | 카카오 닉네임이 실명인 사용자가 많다. 현행대로면 **실명이 그룹 화면과 공개 게시판에 영구 노출**되고 변경 API도 없다. 익명 서비스 컨셉과 정면 충돌 |
| **영향** | 와이어프레임에 프로필 화면이 없어 프론트 충격은 작음. 다만 요구6-3의 "프로필 삭제" 조항은 대상이 사라지므로 문구 정리 필요 |
| **승인 필요** | ☐ 승인 ☐ 원문대로 저장 |

### 2. 알림 3종 → **v1 미구현(폴링 대체)**

| | |
|---|---|
| **원문** | 요구2-2 결과: "전원에게 **매칭 완료 알림이 발송**되며" / 요구3-2 결과: "인증 작성자에게 **응원 알림**이 전달된다" / 요구6-2 결과: "운영관리자에게 **기한 초과 알림**이 전달되고" |
| **변경** | 알림 기능 전체 미구현. 클라이언트 폴링으로 대체 |
| **이유** | 푸시 알림은 FCM 연동·기기 토큰 관리·발송 서버가 필요해 MVP 범위를 크게 넘어선다 |
| **영향** | **와이어프레임 화면7에 "대기 중 앱을 닫아도 매칭이 완료되면 알림을 드려요"라는 문구가 이미 있다** — 문구 삭제 또는 알림 구현 중 택일 필요. 매일 인증이 핵심인 서비스에 리마인더가 없다는 점도 함께 판단 요망 |
| **승인 필요** | ☐ 미구현 승인 ☐ 인앱 알림만 구현 ☐ 푸시까지 구현 |

### 3. AI 인증 진위 판별 → **재사용 탐지만 실동작, 관련성·도용은 로깅만**

| | |
|---|---|
| **원문** | 요구7-1: "**동일 사진 재사용, 인터넷 도용 이미지, 목표와 무관한 피사체** 등을 탐지" / "이미지를 분석해 선택된 목표 분야와의 **관련성 점수를 계산**한다" |
| **변경** | ① 재사용 탐지는 **같은 회원의 과거 인증만** 대조(타인 사진 도용·그룹 내 돌려쓰기 미탐지) ② 관련성 점수는 **shadow 모드**(계산·로깅만 하고 차단하지 않음) ③ 인터넷 도용 탐지는 미구현 |
| **이유** | 관련성 판정은 멀티모달 AI가 필요하고 오탐 시 정상 인증이 막히는 위험이 크다. 초기엔 데이터를 모아 임계값을 잡은 뒤 차단을 켜는 것이 안전 |
| **영향** | **PRD 페르소나(김도윤)가 "아무도 진지하게 검수하지 않는다는 느낌 때문에 3일 만에 이탈"이라며 이 기능의 근거로 명시돼 있다.** 실동작이 재사용 탐지 1축뿐이면 그 근거가 약해진다 |
| **승인 필요** | ☐ shadow로 시작 승인 ☐ 관련성 차단까지 v1에 포함 |

### 4. 신고 시 "신고자 그룹 접근 차단" → **해석 미확정, 현재 미적용**

| | |
|---|---|
| **원문** | 요구4-2: "신고가 접수되고 동시에 **신고자의 해당 그룹 접근이 차단된다**" / PRD 시나리오: "신고 후 **바로 그룹 접근을 종료**한다" / PRD 타겟: "**스스로 관계를 끊을 수 있기를** 원하는 안전 요구" |
| **변경** | 두 해석이 가능해 확정 보류. **(a) 신고자를 그룹에서 내보낸다** vs **(b) 신고 대상만 신고자에게 안 보이게 한다(뮤트)** |
| **문제** | (a)로 하면 **신고 = 내 챌린지 포기**가 되고, 그룹 평균 분모가 잔류자만 세므로 **성적이 나쁜 사람이 종료 직전 아무나 신고하면 완주에 유리**해진다. 안전 기능이 정반대로 작동 |
| **원문 근거** | 위 3곳 모두 (a)를 시사한다 |
| **승인 필요** | ☐ (a) 퇴장 ☐ (b) 뮤트 ☐ (a)+완주 판정 보정 |

### 5. AI 얼굴 탐지 → **인증 사진에 얼굴이 나오면 거부**

| | |
|---|---|
| **원문** | 요구7-2: "이미지에서 … **식별가능 개인정보(얼굴**·신분증·차량번호 등)를 탐지" + "고위험이면 공개 차단" ↔ 요구3-1: "사용자가 **캠을 켜거나** 사진을 촬영해 업로드" |
| **변경** | 얼굴 감지 시 **저장하지 않고 422로 거부 + "얼굴이 나오지 않게 다시 찍어주세요" 안내**. 캠 인증은 유지하되 피사체 가이드 변경(책상·노트·운동기구 촬영) |
| **이유** | 원문 두 조항이 그대로면 캠 인증이 전량 차단된다. 익명 서비스이므로 얼굴을 아예 안 올리게 하는 것이 컨셉과 정합 |
| **영향** | 와이어프레임 화면12(캠 인증)에 얼굴 관련 안내가 없어 문구 추가 필요 |
| **승인 필요** | ☐ 얼굴 거부 승인 ☐ 본인 얼굴은 허용 |

### 6. 탈퇴 후 재가입 차단 해시 저장 — **원문에 없는 신설**

| | |
|---|---|
| **원문** | 요구6-3: 유예 종료 시 SNS 식별자를 **자동 삭제**한다 (재가입 차단 언급 없음) |
| **변경** | 영구 제재 이력자에 한해 `HMAC(제공자+식별자)` 해시를 별도 테이블에 남기고 재가입을 거부 |
| **이유** | 이게 없으면 **영구 제재 → 탈퇴 → 30일 후 같은 계정으로 재가입**이 되어 제재 체계가 무력화된다 |
| **영향** | 개인정보 해시를 장기 보관하므로 **개인정보 처리방침에 근거를 넣어야 한다**. 원문 "자동 삭제" 약속과 충돌 소지 |
| **승인 필요** | ☐ 승인(처리방침 반영) ☐ 미도입(제재 우회 감수) |

## 원문 자체의 모순 — 팀이 정해줘야 할 것 (설계 문제 아님)

| # | 충돌 |
|---|---|
| ① | **얼굴 검열 ↔ 캠 인증** (위 5번) — 원문 두 조항이 서로를 무효화한다 |
| ② | **차단 콘텐츠 보관 규칙 부재** — "AI가 차단한 콘텐츠는 관리자 검토로만 복구된다"고 했는데, 복구하려면 유해물 원본을 보관해야 한다. 보관 근거·기간이 원문에 없다 |
| ③ | **텍스트 상호작용 존재 여부** — "응원 대화", "응원 텍스트 외의 폭언 탐지", "그룹 채팅"이 3곳에 나오는데 응원 스티커 기능에는 텍스트 입력이 없다. 채팅은 팀장이 "없어도 된다"로 확정했으나 **"응원 대화"의 처분은 미확정** |
| ④ | **매칭: 유사 vs 동일** — PRD는 "관심사가 **유사한** 6명", 요구2-2는 "**동일** 매칭 조건 참여자만". 매칭 완화(T1-5)의 근거가 PRD 쪽에 있다 |
| ⑤ | **기한 초과 신고의 이용 제한** — PRD 리스크는 "임시 이용 제한을 **적용**", 요구6-2는 "검토 **플래그**로 걸어둔다" |

# MoLock 프로젝트 개요 (2026-08-12)

> 이 파일이 프로젝트 입구다. 작업 전·중·후에 여기부터 본다.
> 백엔드 담당: 홍화수 · 스택: Spring Boot 4.1 / Java 21 / JPA / H2→MySQL

## 1. 한 줄 정의

하루 목표 시간 하나만 고르면 같은 시간을 고른 6명과 자동으로 묶여, 실시간 캠
세션에서 함께 공부하는 서비스다.

## 2. 피벗 경위

이 프로젝트는 원래 모락 — 하루 한 장 사진을 올려 인증하는 6인 챌린지였고,
그 기준으로 기능명세·API·DB·구현 순서까지 정본을 만들어 0·1단계 코드를 작성했다.
2026-08-12 팀이 기획을 MoLock으로 전환했다. 사진 인증 대신 실시간 캠 세션에서
함께 공부하고, AI가 자리비움을 감지하며, 완주가 Streak과 포인트로 쌓여 스토어에서
쓰이는 구조다. 전환 범위가 커서 `제출문서/모락_범위조정_제안.txt`의 절단선으로
v1 범위를 잘라내고, 그 선을 기준으로 문서 정본을 개정했다.

코드 패키지와 레포명은 `morak`을 유지한다. 문서의 서비스 표기만 MoLock이다.

## 3. 핵심 루프

```
목표 기간 설정(7·14·30일)
  → 하루 목표 시간 선택(60·120·180·240분) → 6인 자동 매칭
  → 실시간 캠 세션 참여(LiveKit) → '오늘 할 일' 한 줄 등록
  → 세션 중 자리비움 감지: 60초 초과 시 경고, 3회면 퇴출(포인트 차감)
  → 종료 시각까지 남아 있으면 완주 → 포인트 지급 + Streak +1
  → Streak가 목표 기간에 도달하면 목표 달성 + 보너스 포인트
  → 포인트로 스토어에서 상품 주문
```

이의신청·신고·제재는 이 루프의 판정을 사람이 되돌리거나 사용자를 보호하는 경로다.
퇴출 이의가 인용되면 포인트를 원복하고 그날 완주를 소급 인정한다.

## 4. 백엔드 범위

### v1에 넣는 것

- 회원: 소셜 로그인, 만 14세 연령 검증, 약관 동의, 탈퇴 30일 유예
- 목표·Streak: 개인 목표 기간, 일 단위 Streak, 목표 달성 판정
- 매칭: 하루 목표 시간 단일 기준(옵션 4종), 대기 폴링, 10분 만료
- 라이브 세션: LiveKit 접속 토큰, 입퇴장 웹훅, 세션 조회, 오늘의 목표, Pause
- 자리비움: 클라이언트 이벤트 수집, 서버의 경고·퇴출 판정, 이의신청
- 포인트: 원장 기반(웰컴·세션 완주·목표 달성·퇴출 패널티)
- 스토어: 상품 목록·상세, 포인트 전액 결제 주문 1건 플로우
- 결제: 포인트 충전 PG 테스트키 왕복 1회
- 안전·운영: 신고, 재매칭 차단, 제재, 관리자 큐(신고·이의·세션 모니터)
- 스티커: 종류 목록만. 전송은 LiveKit 데이터 채널이라 서버는 저장하지 않는다

| 보류 항목 | 사유 |

## 5. 문서 지도

```
source/molock-requirements.md      요구사항정의서 v1.0 (FR-101~702, NFR)
source/molock-task-breakdown.md    분장표 (MoSCoW P0~P3) — 우선순위 기준
        ↓  원천. 가공하지 않는다. 분쟁 시 기준선
functional-spec.md v5              요구 정본 (원문 + 승인된 변경 + 보류 사유)
        ↓
api-spec.md v2.0                   계약 정본 — 엔드포인트·게이트·상태머신·에러코드
db-schema.md v2.0                  테이블 정본 — 컬럼·제약
        ↓
implementation-plan.md v4          구현 순서 0~12단계 + 단계별 curl 게이트
open-decisions.md                  팀 확인 대기 목록과 그동안 적용할 잠정값
ai-pipeline.md                     자리비움 감지의 모델·임계값·측정 절차 (앱 담당자용)
```

- 프론트가 계약으로 보는 것은 `api-spec.md`다. 구현 중 오류를 발견하면 코드만
  고치지 말고 `api-spec.md`·`db-schema.md`를 함께 고친다.
- `openapi.yaml`은 `api-spec.md` v2.0 기준으로 재생성 완료(2026-08-12). 어긋나면 `api-spec.md`가 정본이다.
- 화면 대조는 `screen-api-map.md`, 프론트 전달 사항은 `frontend-change-requests.md`.
  둘 다 구 모락 24화면 기준의 **구판**이라 지금은 무효다. MoLock 와이어프레임을
  받은 뒤 재작성한다.
- 실습 강의는 `실습강의/`에 있고, 코드가 바뀌면 강의도 함께 고친다.

## 6. 스택

| 영역 | 선택 |
|---|---|
| 런타임 | Java 21, Spring Boot 4.1, Gradle |
| 영속 | JPA / H2(개발, `MODE=MySQL;LOCK_TIMEOUT=3000`) → MySQL 8(운영) |
| 인증 | 소셜 로그인 + JWT. 개발은 `DevSocialClient` 스텁 |
| 실시간 | LiveKit(매니지드). 접속 토큰 발급과 입퇴장 웹훅이 서버 몫 |
| AI 자리비움 | 온디바이스 추론. 서버는 이벤트를 받아 판정만 한다. 영상은 저장하지 않는다 |
| 결제 | PG 테스트키(토스페이먼츠 테스트 모드 잠정). 인앱결제 없음 |

## 7. 진행 상태

```
완료  0 · 0.5 · E · O 단계   골격, enum·ErrorCode·정책값 교체, 엔티티 재편, OpenAPI 재생성
완료  1 · 1.5 단계           회원·JWT·인터셉터·연령 검증·탈퇴, 약관·목표·Streak
완료  2~11단계               매칭 → 라이브 세션 → 경고·퇴출 → 완주·Streak·포인트 → 스토어
                             → 결제 → 신고·제재 → 관리자·이의 → 탈퇴 완결
진행  12단계                 운영 준비 — 외부 실연동 2건 대기
```

1단계의 수정 대상이었던 만 14세 미만 가입 차단(D7)과 웰컴 포인트 지급은 둘 다
반영이 끝났다. 차단은 계정을 만들지 않는 방식으로 전환했고, 웰컴 지급은 포인트
원장이 생긴 6단계에서 구현했다.

12단계에 남은 것은 코드가 아니라 외부 의존이다. 카카오 `SocialClient`와
토스페이먼츠 `PgClient`의 실구현이 계정·키 발급을 기다리고 있고, 그 자리는 dev가
아닌 프로필에서 전부 거절하는 기본 구현이 채우고 있어 운영 프로필로도 기동은 된다.
LiveKit `RemoveParticipant` 호출과 신고 서술 텍스트 검열도 TODO로 남아 있다.

여기에 재기동 내성 이월 3건이 있다 — 재접속 유예 창의 DB 영속화, 배치의 다중 인스턴스
중복 실행 차단, `point_charge` 승인 시각 정합 방어다. 첫 번째가 끝나기 전까지 **v1 배포는
단일 인스턴스가 전제**이며, 세션 진행 중 서버를 재시작하면 끊긴 참가자가 자리에 남은 것으로
계산된다. 셋 다 `implementation-plan.md` 12단계에 상세가 있다.

검증은 세 차례 돌았다. 1차에서 나온 발견 사항을 `d6ff4b5`로 정리했고, 이어 핵심
불변식(동시성·멱등·경계)을 덮는 통합 테스트 40건을 `9398096`으로 추가했다. 2차 전수
코드 리뷰분이 `26b1bbd`, 3차 문서·코드 대조분이 `e6c8e99`다. 3차는 배치 스캔
인덱스와 405·415 응답, 닉네임 프로젝션이 결과물이다.

세부 잔여 항목과 단계별 게이트는 `implementation-plan.md`에 있다.

## 8. 규칙

- 게이트(curl 실측) 통과 없이 다음 단계로 가지 않는다
- main에 직접 커밋하지 않는다. 커밋·푸시는 화수가 직접 한다
- 잠정값은 코드에 박지 않고 `application.yml`의 `morak.*`에 격리한다.
  팀 확정이 오면 코드가 아니라 그 값만 바꾼다

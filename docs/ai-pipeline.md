# 자리비움 감지 파이프라인 (2026-08-14)

> FR-303이 요구하는 온디바이스 AI 감지를 무엇으로, 어떻게, 어디까지 만들지 정한 문서다.
> 감지 코드는 사용자 기기(브라우저)에서 돌고 서버는 판정만 한다(★D4).

## 1. 한 장 요약

| 항목 | 결정 |
|---|---|
| 감지 축 | **자리비움 하나만.** 딴짓·이상행동은 v1에서 뺀다 |
| 모델 | MediaPipe `@mediapipe/tasks-vision` FaceLandmarker (Apache-2.0) |
| 추론 | 단일스레드 SIMD wasm, Web Worker, 2Hz |
| 프레임 | `<video>` + requestVideoFrameCallback (3사 공통 경로) |
| 판정 | 3초 연속 미검출 → 자리비움, 1.5초 연속 검출 → 복귀 |
| 오탐 방어 | 전송 전 **본인 확인 프롬프트**, 저조도·각도 3값 논리, 입장 시 캘리브레이션 |
| 서버 변경 | 판정 경로 **0줄**. 동의 문구와 구간 노출만 추가 |

## 2. 왜 자리비움 한 축인가

요구사항 FR-303은 "자리비움·딴짓·이상 행동"을 요구하고 NFR-301은 오탐률 5% 미만을 요구한다.
이 둘을 함께 만족시키는 조합이 자리비움 한 축뿐이다.

딴짓 축을 뺀 이유는 기술이 없어서가 아니라 **정확도를 증명할 방법이 없어서**다.

- 휴대폰 감지 — 브라우저에서 돌릴 만한 경량 탐지 모델은 COCO 전체 mAP가 25% 대이고
  휴대폰 클래스 개별 정확도는 공개 수치가 없다. 책상 아래로 내리면 원천적으로 안 잡혀
  우회가 자명하고, 무엇보다 **폰이 보이는 것과 딴짓은 같지 않다**(폰으로 인강을 듣는다).
- 시선·고개 방향 — 각도 계산 자체는 된다. 그러나 공부의 기본 자세(고개 숙여 필기)와
  책상 위 폰 보기가 각도상 구분되지 않는다. 운전자 부주의 연구의 임계각은 "정면 주시가
  정상"인 도메인이라 그대로 옮길 수 없고, 공부 상황의 임계각 문헌은 찾지 못했다.
- 졸음 — 학술 근거는 이 축이 가장 탄탄하다(PERCLOS). 다만 눈 크기 개인차로 고정 임계값이
  일반화에 실패하고, 졸면서 자리를 지킨 사람을 차감하는 것이 옳은지가 기술이 아닌 정책
  질문이다.
- 얼굴로 사람을 식별해 대리 착석을 잡는 것 — **v2가 아니라 영구 배제**를 권고한다.
  생체인식정보 처리에 해당하고 서비스의 익명 원칙과 정면으로 충돌한다.

딴짓 축은 정답 라벨이 주관적이라("이 사람이 지금 딴짓 중인가") 5% 미만을 증명할 데이터셋을
팀이 만들 수 없다. 측정할 수 없는 기준을 붙인 채 출시하는 것 자체가 NFR-301 위반이다.
반면 자리비움은 판정이 결정적이라 실제로 측정할 수 있다(8절).

명시적 배제 목록: 화면 공유·탭 감시, 감정·집중도 추정, 오디오 감시, 키보드 활동 감시.
감정 추정은 EU AI Act가 교육 맥락에서 금지 대상으로 분류한 범주라 확장 후보에서도 뺀다.

되살릴 여지가 있는 유일한 형태는 **본인 화면에만 뜨는 알림**이다(예: 졸음 알림).
서버로 보내지 않으므로 오탐 비용이 없고 서버 계약을 전혀 건드리지 않는다.

## 3. 모델 — FaceLandmarker

`@mediapipe/tasks-vision` 1.0.1, Apache-2.0. 같은 패키지 안의 두 후보 중 무거운 쪽을 고른다.

| | FaceDetector | **FaceLandmarker (채택)** |
|---|---|---|
| 모델 파일 | 약 230KB | 3.76MB |
| 성격 | 공식 문서가 "셀피·전면 카메라 최적화"라고 명시 | 랜드마크 추적 + 얼굴 변환 행렬 |
| 고개 숙임 | 정면 위주 모델이라 미검출 위험 | 추적으로 각도 유지, 양호한 조명에서 pitch 40°까지 검출 보고 |
| 각도 측정 | 불가 | **가능 — "고개 숙임 = 재실"을 규칙으로 명문화할 수 있다** |

채택 근거는 마지막 줄 하나다. 이 서비스의 최대 오탐 원인은 **고개를 숙이고 필기하는
정상적인 공부 자세**이고, 각도를 직접 잴 수 있어야 그것을 자리비움과 구분해 규칙으로
못 박을 수 있다. 모델 파일이 16배 크지만 최초 1회 로딩 문제이지 추론 비용의 차이는 아니다.

폴백은 같은 패키지의 FaceDetector다. 모델 파일 교체 수준이라 전환 비용이 거의 없다.

탈락 후보: SCRFD는 성능 근거가 가장 좋으나 사전학습 가중치가 비상업 연구용이라 쓸 수 없다.
YuNet(MIT)은 opencv.js 기본 빌드에 해당 API가 없어 별도 런타임이 필요해 3안으로만 둔다.
transformers.js에는 얼굴 검출 전용 태스크가 없다. TensorFlow.js 계열은 얼굴 검출 구현이
2025-02 아카이브됐다 — **기획서에 적힌 TensorFlow.js는 쓸 수 없다.**

## 4. 실행 구조

```
LiveKit 로컬 트랙
  → <video> + requestVideoFrameCallback   (프레임 취득)
  → createImageBitmap → Worker transfer
  → [Worker] FaceLandmarker 추론 2Hz → 상태기계
  → [메인] 확인 프롬프트 UI + 전송 큐 → POST /api/sessions/{id}/absence-events
```

**프레임 취득은 한 경로로 통일한다.** 최신 API(MediaStreamTrackProcessor)는 Firefox에 아직
없고(트래커 목표일 2027-01), Chrome과 Safari도 스펙 세대가 달라 구현이 갈린다. 3사 공통
경로인 rVFC 하나로 가면 코드 표면이 1/3이 되고, wasm 추론에서는 어느 경로든 CPU 복사
총량이 같아 성능 손해가 미미하다. 브라우저별 최적화는 v1.1로 미룬다.

**wasm은 단일스레드 SIMD로 고정한다.** 멀티스레드를 고르면 SharedArrayBuffer 때문에
COOP/COEP 헤더가 강제되고, 그러면 **소셜 로그인 팝업이 깨지고** CORP 헤더 없는 서드파티
리소스가 전부 차단된다. 배포를 막을 수 있는 가장 큰 요인이었고, 단일스레드 고정으로 소멸한다.
WebGPU는 이 파이프라인에 불필요하다(MediaPipe의 GPU 위임은 WebGL2를 쓴다).

추론은 2Hz로 시작하고 발열이 감지되면 1Hz로 낮춘다. 경고 임계가 60초라 더 자주 볼 이유가 없다.
주된 부하는 추론이 아니라 6인 영상 수신·송출이므로, 저사양 기기의 한계는 실측으로만 답이 나온다.

모델과 wasm은 CDN이 아니라 자체 호스팅하고 매칭 대기 화면에서 미리 받아 둔다.

## 5. 감지 상태기계와 본인 확인 프롬프트

### 전이

```
PRESENT
  → (첫 미검출, 이 시각이 t0)          OBSERVING
  → (6프레임 연속 미검출 = 3초)         CANDIDATE
  → (t0 + 30초)                        PROMPTING   "자리에 계신가요?"
       ├ 탭함    → DEFERRED (120초 유예 후 재관찰)
       └ 15초 무응답 → ABSENT_SENT      START 전송 (occurredAt = t0)
  → (3프레임 연속 검출 = 1.5초)         END 전송 (occurredAt = 첫 재검출 시각)
```

핵심은 **확인 프롬프트를 통과하기 전에는 서버로 보내지 않는다**는 것이다. 탭 한 번으로
해제되면 서버 데이터에 오탐 구간이 아예 남지 않는다. 응답이 없으면 START를 보내되
**시각은 처음 얼굴이 사라진 t0로 적는다** — 서버는 과거 시각을 허용하므로 60초 판정이
지연 없이 정확하게 계산된다.

프롬프트를 3초가 아니라 30초에 띄우는 이유는 공부 중 방해를 줄이기 위해서다. 60초 임계까지
30초가 남은 시점이라 응답할 시간이 충분하다.

**화장실처럼 진짜 자리를 비운 경우** 탭할 사람이 없으므로 무응답 경로로 흘러 기존과 똑같이
동작한다. 즉 이 장치는 오탐만 걸러내고 정탐은 그대로 통과시킨다.

### 회피 가능성에 대한 판단

탭으로 자리비움을 무한정 미루는 부정 사용이 가능하다. 다음과 같이 제한한다.

- 탭 1회당 유예는 120초까지(반복 시 240/360으로 늘려 소모를 줄인다). 만료되면 다시 묻는다.
- 마지막까지 응답이 없으면 START를 보내되 시각은 **마지막으로 탭한 시각**으로 적는다.
  탭을 그 순간의 재실 증거로 인정하는 것이다.
- 3회 연속으로 해소되지 않으면 카메라 각도·조명 조정을 안내한다.

채택하지 **않은** 제한 둘을 남긴다. "탭한 뒤에도 얼굴이 안 보이면 무효화"는 그 조건이 정확히
고개 숙임 오탐이라 장치의 목적을 죽인다. "세션당 횟수 상한"은 각도 문제로 상한을 소진한
사용자를 구제 불능으로 만든다.

서버가 개입하는 형태(경고 직전에 서버가 확인을 요청)는 검토 후 뺐다. 확인 응답도 결국
클라이언트가 보내는 것이라 신뢰가 더해지지 않는 반면, 서버는 판정 시점을 이벤트 도착
기준에서 타이머 구동으로 바꿔야 하고 지금 없는 푸시 채널까지 필요해진다.

## 6. 최악 조건 — 저조도 × 고개 숙임

조명이 나쁘면 각도 내성이 급락한다는 근거가 있다(불량 조명에서 30° 기울임 검출률 30%).
밤에 스탠드만 켜고 고개 숙여 필기하는 사용자가 정확히 이 교집합에 있다.

**검출 결과를 두 값이 아니라 세 값으로 다룬다.**

| 값 | 조건 | 처리 |
|---|---|---|
| HIT | 신뢰도 ≥ θ_hi | 재실 |
| UNCERTAIN | θ_lo ≤ 신뢰도 < θ_hi | **미검출 카운터를 동결**한다 |
| MISS | 신뢰도 < θ_lo | 미검출로 센다 |

판단이 애매한 구간을 "없음"으로 세지 않는 것이 요점이다. 다만 무한 보류를 막기 위해
동결은 구간당 10초(저조도 모드에서는 20초)까지만 허용하고 그 뒤에는 MISS로 격하한다.

프레임 밝기로 저조도를 감지하면 θ_lo를 완화한다. 대가는 진짜 이석의 확정이 늦어지는 것인데,
`occurredAt`이 첫 미검출 시각으로 기록되므로 서버의 60초 계산은 왜곡되지 않는다.
오탐과 미탐 중 오탐의 비용이 훨씬 크므로 이 맞바꿈을 택한다.

**입장 전 캘리브레이션** — 매칭 대기 화면에서 8초(16프레임) 동안 평상시 자세를 재서 개인별
기준을 잡는다. 신뢰도 임계, 기대 얼굴 크기(멀리 있는 포스터·사진의 유령 검출 배제), 기준 각도,
조도. 값은 브라우저 로컬에만 두고 서버로 보내지 않는다(영상 파생물 무저장 원칙과 정합).
조명이 부족하면 안내는 하되 입장을 막지는 않는다.

## 7. 서버와의 접점

**판정 경로는 한 줄도 바뀌지 않는다.** 클라이언트는 지금 계약 그대로 START/END와 순번,
발생 시각만 보낸다. 5초 간격 제한과 순번 기반 중복 제거도 그대로다.

지켜야 할 규약 셋을 명세에 못 박는다.

1. 보내는 시각은 판단이 끝난 시각이 아니라 **실제로 얼굴이 사라진 프레임의 시각**이다.
   서버가 그 간격으로 60초를 계산하기 때문이다.
2. 429(너무 잦음)를 받으면 **같은 순번으로** 5초 뒤에 다시 보낸다. 새 번호를 매기면 중복
   제거가 깨진다. 순번은 브라우저 세션 저장소에 보존한다 — 유실 후 0부터 다시 시작하면
   서버가 중복으로 보고 새 이벤트가 조용히 사라진다.
3. 관측하지 않은 시간에는 사건을 만들지 않는다. 탭이 백그라운드로 가서 추론이 멈춘 구간은
   보고하지 않고, 서버도 보고가 없으면 판정하지 않는다(★D13). 다만 이미 START를 보낸
   상태라면 복귀 후 END를 반드시 보낸다 — 짝이 없으면 세션 종료 시각까지 자리비움으로
   정산되기 때문이다.

서버에 추가로 필요한 것은 판정이 아니라 **구제**다.

- 캠 분석 동의 문구에 자동 판정 사실과 기준 수치(60초/3회/-300P), 이의 경로, 다른 참가자
  5인에게 영상이 송출된다는 사실을 넣는다. 문구를 고치면 재동의가 필요하다.
- 경고의 근거가 된 미검출 구간(시작·종료·지속 초)을 **본인에게 보여준다.** 영상을 저장하지
  않아 사용자가 다툴 증거가 없다는 문제를, 서버가 이미 갖고 있는 시각 기록을 노출하는
  것으로 해결한다. 추가 수집이 전혀 없다.
- 관리자가 이의를 심사할 상세 API. 지금은 사용자가 쓴 이의 사유조차 관리자 응답에 없어
  심사가 성립하지 않는다.

## 8. 오탐률을 어떻게 증명하나

NFR-301에는 분모가 없다. 다음과 같이 정의한다.

> **오탐률 = 부여된 경고 중 잘못 부여된 경고의 비율.** 사용자가 실제로 입는 피해와 일치한다.

측정은 정답 라벨 구간에 **서버와 동일한 60초 규칙**을 돌려 "정답 경고 시퀀스"를 만들고
실제 발생한 경고와 ±10초로 대조한다. 이렇게 하면 "30초 물 마시러 감"처럼 임계 미만이라
경고가 없어야 정상인 경우가 자동으로 옳게 처리된다. 미탐은 90초 이상 이석에서 경고가
누락된 것으로 정의한다.

**합격 기준** — 팀원 6명이 2시간씩(총 12시간) 재실 대본을 녹화해 **오경고 0건**,
90초 이상 이석 48건 중 **46건 이상** 경고 발생.

정직한 한계를 함께 적는다. 12시간 무사고는 "5% 미만"의 증명이 아니라 발생률 상한이
시간당 0.25건이라는 뜻이다. 비율의 최종 검증은 출시 후 **이의신청 인용률**로 넘어간다.
측정하지 않은 채 5% 달성이라고 적는 선택지는 없다.

대본은 인당 80분이고 고개 숙여 필기하는 자세가 가장 큰 비중을 차지한다. 기기 3종·조명 3종·
안경 유무를 6명에게 배정해 각 축을 최소 3회 덮는다. 라벨링은 사후에 영상을 다시 보는
방식이 아니라 녹화 중 스톱워치로 이석 시각만 찍는 방식이라 인당 정리 10분이면 끝난다.

하네스는 **추론과 판정을 분리**한다. 영상마다 추론은 한 번만 돌려 프레임별 신뢰도를 로그로
남기고, 임계값 튜닝은 그 로그 위에서 재계산한다. 재녹화·재추론 없이 몇 초 만에 결과가
나와야 튜닝이 성립한다. 측정은 실제 서비스와 동일한 라이브러리·모델로 브라우저에서 돌린다.

합격하지 못하면 조정할 손잡이는 순서대로 검출 신뢰도 하향, 미검출 판정 시간 3초 → 5초,
검사 주기, 모델 교체다. 서버의 60초 임계와 간격 제한은 이미 설정값으로 빠져 있고,
클라이언트 감지 파라미터는 클라이언트에 둔다 — 서버로 빼면 "판정은 서버, 클라이언트는
사실 보고만"이라는 경계가 흐려진다.

## 9. 위험과 법적 고려

이 설계에서 가장 무거운 것은 모델 정확도가 아니라 **AI 판정이 곧바로 불이익이 되는 구조**다.

선행 사례가 일관된 신호를 준다. 강제로 감시하는 시험 감독 업계에서조차 AI 단독 판정은
철회됐다 — 한 업체는 2021년 AI 전용 상품을 중단했고(AI가 띄운 경고의 11%만 사람이 검토),
다른 업체는 흑인 얼굴의 57%를 감지하지 못한 검증 결과가 보고됐다. 미국에서는 방 스캔이
위헌 판결을 받았고 유럽에서도 인권 심리가 이어졌다. 시험처럼 회피할 수 없는 상황에서도
그랬다면, 자발적으로 쓰는 서비스에서 억울한 퇴출은 곧 이탈이다.

실제로 "실시간 캠 + AI 자리비움 감지 + 자동 제재"를 함께 하는 소비자 서비스는 확인되지
않았다. 감지까지 하고 알림에서 멈추거나, 제재는 하되 판정 주체가 사람이거나 둘 중 하나였다.

법적으로 확인이 필요한 지점은 셋이다(법률 자문이 아니라 위험 지점의 표시다).

- 얼굴이 있다·없다만 판별하고 누구인지 식별하지 않으며 영상이 서버를 거치지 않는 현재 구조는
  민감정보 규제의 "특정 개인을 알아볼 목적"에 해당하지 않을 가능성이 높다. 얼굴 재식별로
  확장하면 이 판단이 뒤집힌다.
- AI 판정으로 퇴출·차감이 자동 집행되는 것은 **완전히 자동화된 결정**에 해당할 수 있다.
  그렇다면 판단 기준을 공개하고 설명 요구에 답할 의무가 따른다. 사람이 다시 보는 절차
  (이의신청)는 이미 갖춰져 있다.
- 현금으로 산 포인트를 AI 판정에 따른 벌금으로 깎는 구조는 다툼의 소지가 있다.
  결제를 열기 전에 정해야 하고, 팀 결정 항목으로 올려 두었다(open-decisions C-7).

## 11. 아직 확인하지 못한 것

- 고개 숙임 자세만 다룬 공개 벤치마크는 존재하지 않는다. **모델 확정은 실측이 해야 한다**
  (각도 스윕 × 저조도 교차).
- iOS Safari에서의 실제 동작은 실기기 확인이 필요하다.
- 문서의 수치(3초·1.5초·30초·120초·8초, 신뢰도 임계)는 전부 설계 초기값이며 8절의 측정으로
  조정한다.
- 사진이나 대리인으로 속이는 것은 v1에서 막지 못한다. 영상을 저장하지 않기로 한 결정과
  같은 급의, 받아들인 한계다.
- 라이브러리 로딩 용량은 선택한 모델 기준으로 다시 재야 한다. 실행 환경 조사에서 잡은
  수치는 가벼운 검출기 기준이었다.

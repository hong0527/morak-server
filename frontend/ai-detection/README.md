# MoLock 자리비움 감지 — 레퍼런스 구현

온디바이스 자리비움 감지 파이프라인과 오탐률 측정 하네스다.

**무엇을 왜 이렇게 정했는지는 여기 없다.** 그건 `morak-server/docs/ai-pipeline.md`에 있고
그 문서가 계약이다. 이 README는 **어떻게 실행하고 무엇을 채워야 하는지**만 적는다.

이 코드는 브라우저에서 실동작 검증을 하지 못한 상태다. 타입 검사와 판정 로직 자체 점검까지만
끝나 있다(아래 "검증한 것과 못한 것").

---

## 1. 5분 안에 돌려보기

```bash
cd ai-detection
npm install
npm run vendor      # tasks-vision 런타임 + face_landmarker.task(3.76MB)를 harness/vendor 로
npm run build
npm run selftest    # 상태기계·서버규칙·하네스 판정 자체 점검 (브라우저 없이 돈다)
```

`selftest`가 전부 통과하면 판정 로직은 설계 문서대로 도는 것이다.
모델 추론과 카메라는 브라우저에서만 확인할 수 있다.

서버 계약까지 확인하려면 **서버를 띄운 채로** 한 단계를 더 돌린다.

```bash
# 터미널 1 — morak-server 에서
./gradlew bootRun --args='--server.port=8130'

# 터미널 2 — 여기서
npm run contract    # 실제 서버에 SS-4 를 쏴 본다 (브라우저 없이 돈다)
```

`contract`는 6인 매칭으로 세션을 하나 열고, 이 폴더의 전송 계층(`sender.ts`·`seq-store.ts`)이
만드는 요청을 그대로 보낸다. 본문 형식·과거 시각 허용·429 재전송·409 중복 처리를 확인한다.
서버 주소는 `MORAK_BASE_URL` 로 바꿀 수 있다.

**브라우저 경로까지 확인하려면** 카메라 없이도 된다. 크롬에 가짜 카메라를 물린다.

```bash
npm run browser-check          # 헤드리스 크롬 + 합성 영상. 전송은 대역(stub)

# 서버까지 이어 보려면 (morak-server 를 8160 에 dev 프로필로 띄운 뒤)
npm run build && npm run build:worker
node harness/browser-check.mjs --classicWorker=1 --server=http://localhost:8160 \
  --fastPrompt=1 --skipCalibration=1 --runMs=32000
```

getUserMedia → `frame-source` → Worker → 상태기계 → `sender` → SS-4 가 실제 브라우저에서
한 줄로 이어지는지 본다. 사람이 눈으로 볼 때는 `harness/live-page.html` 을 직접 열면 된다.
**확인되는 것은 "파이프라인이 끝까지 돈다"까지다** — 합성 영상은 사람 얼굴이 아니므로
정확도는 여기서 나오지 않는다(8절).

> `ffmpeg` 가 필요하다(y4m 생성). 없으면 이 확인만 건너뛴다.
> 붙이기 전에 **9-9 를 먼저 읽어라** — Worker 는 클래식이어야 한다.

## 2. 폴더에 뭐가 있나

### 감지 파이프라인 (`src/`)

| 파일 | 역할 |
|---|---|
| `types.ts` | 3값 판정·상태·Effect·SS-4 본문 타입 |
| `config.ts` | 튜닝 파라미터 전부. **여기 값은 전부 설계 초기값이고 확정값이 아니다** |
| `frame-source.ts` | `<video>` + requestVideoFrameCallback 프레임 공급자. 카메라를 새로 열지 않는다 |
| `detector.ts` | FaceLandmarker 래퍼. 프레임 → 원시 특징(검출 여부·얼굴 크기·각도) |
| `luminance.ts` | 프레임 밝기. 저조도 모드 판정용 |
| `scoring.ts` | 원시 특징 → 0~1 점수 → HIT/UNCERTAIN/MISS. **가장 많이 손볼 파일이다** |
| `state-machine.ts` | 전이표 구현. 순수 객체 — 네트워크도 DOM도 모른다 |
| `calibration.ts` | 입장 전 8초 캘리브레이션과 로컬 저장 |
| `server-rule.ts` | 서버 판정 규칙 재현(임계 60초 + 길이 비례 경고). **클라이언트 판정에 쓰지 않는다.** 하네스 대조 전용. **서버 값이 바뀌면 여기도 바꿔야 한다** |
| `worker/detector.worker.ts` | Worker 엔트리. 추론 + 상태기계가 여기서 돈다 |
| `worker/protocol.ts` | 메인 ↔ Worker 메시지 계약 |
| `client/seq-store.ts` | clientSeq·미전송 큐·열린 START 를 sessionStorage 에 보존 |
| `client/sender.ts` | SS-4 전송 큐. 5초 페이싱, 429 재전송, 응답 해석 |
| `client/controller.ts` | 메인 스레드 오케스트레이터. 앱이 직접 만지는 것은 이 클래스 하나다 |

### 측정 하네스 (`harness/`)

| 파일 | 역할 |
|---|---|
| `record-page.html` | 브라우저에서 클립 하나를 추론해 로그 JSON 을 내려받는다 |
| `record.ts` | 그 추론 루프. **영상당 딱 한 번 돈다** |
| `log-format.ts` | 추론 로그와 정답 라벨의 스키마 |
| `replay.ts` | 로그 위에서 판정 재계산. 추론하지 않는다 |
| `score.ts` | 정답과 대조해 오탐률·미탐 계산 |
| `cli.ts` | `score` / `sweep` 명령 |
| `selftest.ts` | 합성 입력으로 판정 로직 확인 |
| `server-contract.ts` | 실제 서버에 SS-4 를 쏴 계약 정합 확인. 서버가 떠 있어야 한다 |
| `w1-check.mjs` | 탭을 닫았다 재입장하는 시나리오를 실제 서버에 대고 재현한다(9-10). 서버가 떠 있어야 한다 |
| `labels.example.json` | 정답 라벨 예시 |
| `modelcheck.mjs` | **모델 비교용.** 같은 프레임을 FaceLandmarker(VIDEO/IMAGE)·FaceDetector·PoseLandmarker 넷에 동시에 먹이고 변환행렬 원본 16개 값을 남긴다 |
| `modelcheck-analyze.mjs` | 그 로그에서 검출률·추론시간·행렬 성질·각도 이상치를 표로 낸다 |

`modelcheck*` 둘은 **비교 전용이고 서비스 코드가 아니다.** 모델 선택을 다시 의심할 일이
생기면 여기서 시작하면 된다 — 6-1 의 표가 이것으로 나왔다.

## 3. 앱에 붙이는 법

```ts
import { AbsenceDetectionController, FetchAbsenceTransport } from "./ai-detection/src/index.js";

const controller = new AbsenceDetectionController({
  // 이미 LiveKit 로컬 트랙이 붙어 있는 video 엘리먼트를 넘긴다. 새로 만들지 마라.
  video: localVideoElement,

  // ** 이 둘을 반드시 넘겨라. 안 넘기면 탭을 닫았다 다시 들어온 사용자의 감지가
  //    통째로 꺼질 수 있다(9-10). SS-1 이 내리는 값을 그대로 쓰면 된다. **
  sessionStartedAtMs: Date.parse(session.startedAt),
  memberId,

  // Worker 생성 문법은 번들러마다 다르다. 그래서 앱이 준다.
  // ** 반드시 클래식 워커여야 한다. type: "module" 을 주면 모델이 로드되지 않는다(9-9). **
  // 번들러로 IIFE 한 덩이를 뽑아 그 URL 을 준다:
  //   npx esbuild dist/src/worker/detector.worker.js --bundle --format=iife \
  //     --platform=browser --target=es2022 --outfile=dist/worker-classic.js
  createWorker: () => new Worker(workerUrl),

  sessionId,
  assets: {
    wasmBasePath: "/ai/wasm",                    // 자체 호스팅 경로
    modelAssetPath: "/ai/face_landmarker.task",
  },
  transport: new FetchAbsenceTransport(
    `/api/sessions/${sessionId}/absence-events`,
    () => ({ Authorization: `Bearer ${accessToken}` }),
  ),
  hooks: {
    onShowPrompt: () => setPromptVisible(true),
    onHidePrompt: () => setPromptVisible(false),
    onShowAdjustHint: () => toast("카메라 각도나 조명을 조정해 주세요"),
    onServerVerdict: (res) => {
      setWarningCount(res.warningCount);
      if (res.evicted) goToEvictedScreen(res.evictionId);
    },
    onTerminal: (code) => console.warn("감지 종료:", code),
    // 토큰 만료. 감지는 계속 돌고 이벤트는 큐에 쌓인다 — 다시 로그인시킨 뒤
    // resumeAfterReauth() 를 부르지 않으면 세션이 끝날 때까지 하나도 안 나간다(9-11).
    onAuthExpired: async () => {
      await reLogin();
      controller.resumeAfterReauth();
    },
  },
});
```

호출 순서:

```ts
// 매칭 대기 화면에서 — 모델을 미리 받아 두고 캘리브레이션을 잡는다
await controller.init();
const { profile, warnings } = await controller.calibrate();   // 8초
// warnings 에 LOW_LIGHT 가 있으면 안내만 한다. 입장을 막지 않는다.

// 세션 입장 후
controller.start();

// 프롬프트를 탭했을 때
controller.tapPrompt();

// 화장실 모드(SS-5)가 200 으로 성공한 "뒤에". **응답을 함께 넘긴다**
// — 넘기지 않으면 그때 붙은 경고를 사용자가 모른 채 다음 경고에 퇴출된다(9-12).
controller.onRestroomStarted(ss5Response);
// 복귀(SS-6) 뒤에
controller.onRestroomEnded();

// 세션을 떠날 때
controller.dispose();
```

`onRestroomStarted()`를 SS-5 성공 뒤에 부르는 것이 중요하다. 서버가 그 시각으로 열린
자리비움 구간을 대신 닫으므로 클라이언트는 END 를 보내지 않아야 하고, 아직 보내지 않은
START 도 버려야 한다. 먼저 부르고 SS-5 가 409 로 실패하면 상태가 어긋난다.

## 4. 서버 계약에서 절대 어기면 안 되는 것

`open-decisions.md` C-2 의 7가지를 여기서 다시 짚는다. 이 구현이 각각을 어디서 지키는지도 적는다.

| # | 주의사항 | 이 구현에서 |
|---|---|---|
| ① | **얼굴 감지는 Web Worker 에서.** MediaPipe 의 영상 감지 함수는 호출 중 스레드를 붙잡아 메인에서 돌리면 캠 화면이 끊긴다 | `worker/detector.worker.ts`. 추론과 상태기계가 전부 Worker 안이다 |
| ② | **초당 2~5회면 충분하다.** 배터리 소모는 이 횟수가 거의 결정한다 | `config.stateMachine.inferenceHz = 2`. 발열이 보이면 1로 낮춘다 |
| ③ | **한 장 안 보였다고 바로 START 를 보내지 마라.** 얼굴은 경계에서 깜빡이고, 5초 간격 제한 때문에 뒤따르는 END 가 버려져 자리에 있는 사람이 계속 자리비움으로 남는다 | 6프레임(3초) 연속 미검출 + 30초 대기 + 프롬프트 무응답 15초를 모두 통과해야 START 가 나간다. 복귀는 3프레임 연속 검출을 요구해 START/END 가 튀지 않게 막는다 |
| ④ | **429 를 받으면 5초 뒤 같은 clientSeq 로 재전송한다.** 새 번호를 매기면 서버의 중복 제거가 깨진다 | `client/sender.ts`의 `RATE_LIMITED` 분기. 큐에서 빼지 않고 그대로 다시 보낸다 |
| ⑤ | **오탐 테스트에 "고개 숙이고 필기하는 자세"를 반드시 넣어라.** 가장 큰 위험이다 | 측정 대본(6절)에서 가장 큰 비중. 얼굴이 잡히기만 하면 각도와 무관하게 재실로 본다(`scoring.ts`) |
| ⑥ | **아이폰은 Safari 18.4 이상에서 확인하라.** 그 아래는 속도가 크게 떨어진다 | 확인하지 못했다. 실기기 확인이 남은 일이다 |
| ⑦ | **카메라를 새로 켜지 마라.** 두 번 잡으면 기기에 따라 화면이 멈춘다 | `getUserMedia` 호출이 이 폴더에 한 줄도 없다. `controller` 는 이미 붙어 있는 `<video>`를 받는다 |
| ⑧ | **화장실 모드에서 감지를 멈춰라.** 안 멈추면 화장실에 있던 시간이 자리비움으로 판정돼 경고가 붙는다 | `onRestroomStarted()` 가 프레임 펌프를 멈추고 워커를 IDLE 로 보낸다. **코드는 다 있고 앱이 부르기만 하면 된다** — 실측에서 깨진 것은 부르는 쪽이 없어서였다(9-12) |

여기에 세 가지를 더 붙인다. 전부 `ai-pipeline.md` §7의 규약이다.

- **`occurredAt` 은 판단이 끝난 시각이 아니라 실제로 얼굴이 사라진 프레임의 시각이다.**
  서버가 그 간격으로 60초를 계산한다. START 는 t0(첫 미검출 프레임), END 는 첫 재검출 프레임이다.
  프롬프트를 탭한 적이 있으면 START 시각은 마지막 탭 시각이 된다 — 탭을 그 순간의 재실 증거로
  인정하는 것이다.
- **clientSeq 는 세션 저장소에 보존한다.** 유실하고 0부터 다시 시작하면 서버가 중복으로 보고
  새 이벤트가 조용히 사라진다. `client/seq-store.ts`가 sessionStorage 에 들고 있다.
- **열린 START 는 반드시 END 로 닫는다.** 짝이 없으면 세션 종료 시각까지 자리비움으로 정산된다.
  새로고침으로 상태기계가 사라져도 저장소의 표시를 보고 복원한다(`controller.start()`).
  탭이 백그라운드로 가서 추론이 멈춘 구간은 보고하지 않는다 — 상태기계가 프레임 공백을 감지해
  아무것도 만들지 않는다.

**앱이 부르지 않으면 조용히 깨지는 것 셋.** 전부 실제 서버에 대고 재현된 경로다(P-wiring).

| 무엇을 | 안 하면 | 근거 |
|---|---|---|
| `sessionStartedAtMs` 를 넘긴다 | 탭을 닫았다 다시 들어오거나 기기를 바꾸면 `clientSeq` 가 앞 실행과 겹쳐 서버가 409 로 거절한다. **그 세션의 자리비움이 통째로 사라진다** | 9-10 |
| `onAuthExpired` 에서 재로그인 후 `resumeAfterReauth()` | 토큰이 만료되면 전송이 멈춘 채 큐만 쌓이고 **세션이 끝날 때까지 하나도 안 나간다** | 9-11 |
| SS-5 성공 직후 `onRestroomStarted(응답)` | 화장실에 있던 시간이 그대로 자리비움으로 판정돼 **경고가 붙는다.** 응답을 안 넘기면 그때 붙은 경고를 사용자가 모른다 | 9-12 |

## 5. 오탐률 측정

### 왜 추론과 판정을 나눴나

영상마다 **추론은 한 번만** 돌려 프레임별 원시 특징을 로그로 남기고, 임계값 튜닝은 그 로그
위에서 재계산한다. 재녹화·재추론 없이 몇 초 만에 결과가 나와야 튜닝이 성립한다.

로그에 판정 결과가 아니라 **원시 특징**을 남기는 이유도 같다. 판정값을 굳혀 놓으면 그 로그가
특정 임계값에 묶여 점수 함수(`scoring.ts`)를 바꿀 수 없게 된다.

### 절차

**1) 클립을 추론해 로그를 뽑는다** — 브라우저에서

```bash
npm run build && npm run vendor
mkdir -p harness/logs harness/labels
npx serve .        # 아무 정적 서버든 좋다. file:// 로는 안 된다(모듈·wasm 로딩)
```

`harness/record-page.html`을 열고 클립을 고른 뒤 "추론 시작". 끝나면 `<clipId>.json`이
내려받아진다. `harness/logs/`에 넣는다.

측정은 실제 서비스와 동일한 라이브러리·모델로 브라우저에서 돌려야 한다. 이 페이지가 그 조건을
지킨다 — Node 로 옮기면 wasm 런타임이 달라져 측정 대상이 서비스가 아니게 된다.

**2) 정답 라벨을 쓴다** — `harness/labels/<clipId>.json`

`harness/labels.example.json`을 복사해 쓴다. 라벨링은 사후에 영상을 다시 보는 방식이 아니라
**녹화 중 스톱워치로 이석 시각만 찍는 방식**이다. 인당 정리 10분이면 끝난다.

`clipId`가 로그와 같아야 짝이 맞는다. 시각은 영상 재생 위치(ms) 기준이다.

**3) 채점한다** — Node

```bash
npm run score -- --logs harness/logs --labels harness/labels
npm run sweep -- --logs harness/logs --labels harness/labels
```

`score`는 현재 설정으로 합격 여부를 낸다.
`sweep`은 튜닝 손잡이를 문서가 정한 순서대로 돌려 어떤 설정이 합격선을 넘는지 표로 낸다
(검출 신뢰도 하향 → 미검출 판정 시간 3초→5초 → 검사 주기 → 모델 교체).

### 어떻게 채점하나

1. 정답 라벨 구간에 **서버와 동일한 60초 규칙**을 돌려 "정답 경고 시퀀스"를 만든다.
2. 재계산된 이벤트에도 같은 규칙을 돌려 "실제 경고 시퀀스"를 만든다.
3. 둘을 구간 시작 시각 기준 ±10초로 대조한다.

이렇게 하면 "30초 물 마시러 감"처럼 임계 미만이라 경고가 없어야 정상인 경우가 자동으로 옳게
처리된다 — 정답 쪽에서도 경고가 만들어지지 않기 때문이다.

> **오탐률 = 부여된 경고 중 잘못 부여된 경고의 비율.** 분모가 경고 수이지 프레임 수가 아니다.
> 사용자가 실제로 입는 피해와 일치시킨 정의다.

미탐은 90초 이상 이석에서 경고가 누락된 것으로 센다.

`sweep` 표의 **프롬프트 수**도 함께 본다. 이 값이 크면 오탐이 서버로 안 나가고 프롬프트로
떠넘겨지고 있다는 뜻이다. 오경고 0건이어도 사용자 방해가 크다는 신호로 읽는다.

## 6. 측정 대본과 합격 기준

**합격 기준** — 팀원 6명이 2시간씩(총 12시간) 재실 대본을 녹화해
**오경고 0건**, 90초 이상 이석 48건 중 **46건 이상** 경고 발생.

**대본** — 인당 80분. 고개 숙여 필기하는 자세가 가장 큰 비중을 차지한다.

| 구간 | 시간 | 내용 |
|---|---|---|
| 도입 | 0~8분 | 평상시 자세로 앉아 있기(캘리브레이션 구간이다. 여기서 자리를 뜨지 마라) |
| 필기 | 8~38분 | 고개 숙여 노트 필기. **가장 중요한 구간이다** |
| 화면 | 38~50분 | 화면 보며 타이핑 |
| 이석 A | 임의 | 90초 이상 자리 비우기 × 2회 (스톱워치로 시각 기록) |
| 짧은 이석 | 임의 | 30~50초 자리 비우기 × 2회 (경고가 **없어야** 정상인 대조군) |
| 자세 변화 | 50~65분 | 기지개, 뒤로 젖히기, 옆 사람과 대화, 턱 괴기 |
| 저조도 | 65~80분 | 조명 하나만 켜고 다시 필기 |

기기 3종·조명 3종·안경 유무를 6명에게 배정해 각 축을 최소 3회 덮는다.
배정표는 `labels.json`의 `conditions`에 적어 두면 나중에 세기 쉽다.

**합격하지 못하면 조정할 손잡이는 순서대로** 검출 신뢰도 하향, 미검출 판정 시간 3초 → 5초,
검사 주기, 모델 교체다. `sweep`이 이 순서 그대로 돈다.

> 다만 **필기 구간 검출률이 낮아서 떨어진 경우라면 순서를 뒤집어 모델 교체를 먼저 본다.**
> 임계값 튜닝은 모델이 얼굴을 보고 있을 때만 의미가 있다 — 애초에 못 보는 것을 임계값으로
> 되살릴 수는 없다. 후보와 비용은 6-1 표에 있다.

**정직하게 적을 것** — 12시간 무사고는 "5% 미만"의 증명이 아니라 발생률 상한이 시간당 0.25건
이라는 뜻이다. 측정하지 않은 채 5% 달성이라고 적는 선택지는 없다.

### 6-1. 공개 영상으로 지금 확인한 것 (사람을 부르기 전에)

```
1분 41초 · 1920x1080 · CC0 · 정면 토킹헤드
```

```bash
  https://upload.wikimedia.org/wikipedia/commons/5/59/Identifying_works_in_the_Public_Domain.webm

```

#### 처음 돌렸을 때 나온 것과, 원인을 찾은 뒤 (2026-08-15 → 08-16)

처음 돌렸을 때 검출률이 **67.7%** 로 낮고 `LOW_DETECTION_RATE` 경고가 떴으며 `pitchDeg` 에
**104도짜리 이상치**가 있었다. 원인 후보를 셋으로 적어 두고 미해결로 남겼는데,
**같은 프레임을 다른 구성에도 동시에 먹여 보는 것**으로 답이 나왔다(조사 원본 `ai/O-modelcheck.md`).

원인은 셋 중 하나였다 — **`runningMode: "VIDEO"`.** VIDEO 모드는 직전 프레임의 ROI로 추적을
먼저 시도하는데 우리는 2Hz라 직전 프레임이 500ms 전이다. 그 ROI가 낡아 추적이 어긋나고,
어긋난 crop에 얼굴을 맞추느라 검출을 놓치거나 자세 행렬이 통째로 뒤집힌다.

**"편집 영상이라서"와 "이 얼굴·이 조명에서의 모델 성능"은 원인이 아니었다** —
같은 프레임에서 FaceDetector가 신뢰도 **0.939**(놓친 프레임)와 **0.941**(잡은 프레임)로
구분되지 않는 값을 내고 있었고, PoseLandmarker의 코 visibility는 **1.000** 이었다.
다른 모델 둘이 또렷이 보고 있는 자리에서 이 구성만 못 본 것이다.

**`detector.ts` 를 IMAGE 모드로 바꾼 전후** (같은 영상·같은 명령, `npm run video-check`):

| | 전 (VIDEO) | 후 (IMAGE) |
|---|---|---|
| 전체 검출률 | **67.7%** (201프레임) | **94.1%** (203프레임) |
| 0~90초 구간별 | 61~82% | **95%, 나머지 8구간 전부 100%** |
| pitch 범위 | 중앙 1.8 · **최대 104** | 최소 -12.8 · 중앙 1.1 · **최대 13.3** |
| 1초 이상 미검출 구간 | 여러 곳 | **페이드아웃(95.1~100.7초) 하나뿐** |
| 캘리브레이션 경고 | `LOW_DETECTION_RATE` | **없음** (`warnings: []`) |
| 추론 시간 | — | 20.3ms |

전체 94.1%의 나머지는 전부 **말미 페이드아웃**(밝기 0.23, 검출률 50%)이다. 그 구간을 빼면
사실상 전부 잡는다.

같은 프레임에 네 구성을 동시에 먹여 비교한 값은 이렇다(페이드아웃 제외 160프레임).

| 구성 | 검출률 | pitch 범위 | \|pitch\|>30° | 추론 중앙 | 모델 크기 |
|---|---|---|---|---|---|
| FaceLandmarker VIDEO | 73.1% | -26 ~ +51° | 5건 | 18.8ms | 3.76MB |
| **FaceLandmarker IMAGE** | **99.4%** | **-13 ~ +11°** | **0건** | **15.9ms** | 3.76MB |
| FaceDetector | 99.4% | 각도 없음 | — | 3.7ms | 224KB |
| PoseLandmarker lite | 100.0% | 각도 없음 | — | 16.3ms | 5.51MB |

IMAGE 모드는 **FaceDetector와 프레임 단위로 완전히 일치**했다(양방향 불일치 0건).
그리고 VIDEO보다 **더 빠르다** — VIDEO는 추적에 실패한 뒤 검출로 되돌아가 두 번 일한다.

> **저조도는 여전히 대본으로 확인해야 한다.** 페이드아웃에서 검출률이 떨어지는 것은
> 관측됐지만 의도한 실험이 아니고, 저조도 경로(`thetaLoLowLight`·동결 상한 20초)는
> 그 자체로 시험된 적이 없다.

#### 이 영상으로 **확인되지 않는 것**

- **고개 숙여 필기하는 자세.** 정면 토킹헤드라 그 구간이 아예 없다. **일반 공개 영상에
  거의 없는 자세이고 우리 최대 오탐 원인이라, 이것만은 직접 찍어야 한다**(6-2).
  **위 94.1%가 그 자세에서도 유지되는지가 이 프로젝트의 진짜 질문이고 여전히 미확인이다.**
- **7-1 pitch 부호 규약.** 숙인 구간이 없어 결론이 나지 않았다. 여전히 미결이다.
- **오탐률.** 한 사람·한 조명·편집된 영상이다. 정확도로 옮겨 적으면 안 된다.
  **94.1%를 우리 검출률로 읽으면 안 된다.**
- 저조도·개인차·실기기 성능·6인 동시 실행.
- **IMAGE 모드의 실기기 비용.** 매 프레임 192x192 검출기를 다시 돌린다. 데스크톱 맥에서는
  VIDEO보다 빨랐으나 저사양 안드로이드에서 그 비율이 같은지는 모른다.

실제로 이게 떴다).

| 구간 | 기대 | 어긋나면 |
|---|---|---|
| 정면 | **95% 이상** | 90% 아래면 모델이 이 사람·이 조명을 잘 못 잡는 것이다. `modelDetectionConfidence`(0.2)를 더 낮춰 본다 |
| **필기** | **90% 이상** | 70~90%면 경계다. `minFaceSizeRatio`(0.45)를 낮춘다 — 숙이면 얼굴 상자가 작아져 비율이 떨어진다.<br>**70% 미만이면 설계 전제가 흔들린다.** "고개 숙임 = 재실"을 FaceLandmarker 로 지킬 수 있다는 §3 의 전제다.<br>이때 **모델 교체를 마지막이 아니라 먼저 시도하라.** FaceDetector 는 224KB·3.7ms 로 IMAGE 모드 FaceLandmarker 와 검출이 완전히 일치했고(6-1 표), 모델 카드 보장 범위가 roll·pitch 45° 이내라 필기 자세를 포함한다. 잃는 것은 각도 하나뿐이고 각도는 `liftRecentHeadDown` 한 곳에만 쓰인다 |
| 이석 | **0%에 가깝게** | 20% 넘게 잡히면 배경에 얼굴로 잡히는 것(사진·포스터)이 있다. `minFaceSizeRatio` 를 **올려** 유령 검출을 배제한다 |
| 복귀 | 정면과 같은 수준 | 복귀가 느리면 `returnFramesToPresent`(3프레임=1.5초)를 본다 |

**③ 미검출 구간 목록이 실제 이석과 맞는지 본다.**

이석 구간만 나오면 통과다. **필기 구간 안에 1초 이상짜리가 여럿 끼어 있으면 그것이 오탐의
씨앗이다** — 연속 6프레임(3초)이면 상태기계가 CANDIDATE 로 넘어가고, 30초를 더 버티면
프롬프트가 뜬다. 필기하다 프롬프트를 보는 사용자가 그렇게 만들어진다.

**④ pitch 부호를 확인한다 (7-1 완료 조건).**

표의 `pitch중앙` 열에서 정면 구간과 필기 구간을 비교한다. **최소·최대도 함께 본다** —
IMAGE 모드로 옮긴 뒤 정면 영상의 pitch 범위는 -12.8 ~ 13.3°다. 필기 구간이 이 범위를
크게 벗어나지 않으면 각도로 고개 숙임을 가려낼 여지 자체가 없다는 뜻이므로
`headDownPitchDeg`(15)를 함께 의심하라.

- 필기 쪽이 **더 작으면(음수 방향)** — `scoring.ts` 의 `isHeadDown`(`pitchDeg <= base - 15`)이
  맞다. 그대로 두고 7-1 을 닫는다.
- 필기 쪽이 **더 크면 부호가 반대다.** `isHeadDown` 의 부등호를 뒤집어야 한다. 안 뒤집으면
  저조도 × 고개 숙임 보호 장치가 **정확히 반대로** 동작한다.
- 두 값의 차이가 **15도(`headDownPitchDeg`) 미만**이면 그 임계도 함께 낮춘다. 차이가 안 나면
  보호 장치가 아예 발동하지 않는다.

**⑤ 얼굴 크기 여유를 본다.**

`얼굴크기` 열은 절대값이라 그 자체보다 **정면 대비 필기 구간의 감소폭**이 중요하다.
캘리브레이션 기준의 45%(`minFaceSizeRatio`) 아래로 내려가면 검출돼도 점수가 `presentBaseScore`
(0.35)에 머물러 **HIT 가 아니라 UNCERTAIN** 이 된다. UNCERTAIN 은 미검출 카운터를 동결시킬 뿐
자리비움으로 세지는 않으므로 경고로는 안 가지만, 그 상태가 10초를 넘기면 MISS 로 격하된다
(`uncertainFreezeMs`). 필기 구간 크기가 정면의 절반 근처까지 떨어진다면 `minFaceSizeRatio` 를
0.35 정도로 낮추는 것이 첫 조정이다.

## 7. 담당자가 반드시 채워야 하는 빈자리

번호가 위일수록 먼저 해야 한다.

**7-1. pitch 부호 규약 확인 (필수, 30분)**

`detector.ts`의 `eulerFromColumnMajor`가 뽑는 pitch 가 "고개를 숙일 때 음수"인지 확인하지
못했다. 부호가 반대면 `scoring.ts`의 `isHeadDown` 부등호를 뒤집어야 하고, 그러지 않으면
저조도 × 고개 숙임 보호 장치가 정확히 반대로 동작한다.

**여전히 미결이다.** 공개 CC0 영상으로 확인을 시도했으나 정면 토킹헤드라 고개 숙인 구간이
없어 결론이 나지 않았다.

> **이전 판이 여기 적어 둔 진단은 틀렸다.** "euler 추출이 특정 순간 튄다"고 썼는데
> 추출은 정상이었다. 이상치 프레임의 행렬도 `det=1.000`·직교오차 0인 **멀쩡한 회전행렬**이라
> **자세 추정 자체가 틀린 값을 낸 것**이고, 원인은 `runningMode: "VIDEO"` 였다(6-1).
> 행우선으로 읽었어도 -61.9°가 나와 똑같이 쓰레기다 — 수식을 바꿔 고칠 수 있는 문제가 아니었다.
>
> 열우선 판독이 맞다는 것도 확인됐다: 실제 행렬의 마지막 네 값이 `[0.00, 12.45, -64.08, 1.00]`
> 로 평행이동이 **마지막 열**에 있다. 회전부에 스케일도 없다(544프레임 전부 열 노름 1.0000).
>
> IMAGE 모드로 옮긴 뒤 pitch 범위가 **-12.8 ~ 13.3°** 로 좁아져, 이제 대본 A 한 번이면
> 부호가 깨끗하게 갈린다. 그래도 최소·최대는 함께 볼 것.

확인 방법: **6-2 의 대본 A(60초)** 를 찍어 `npm run video-check` 로 돌리고, 표의 `pitch중앙`
열에서 정면 구간과 필기 구간을 비교한다. 필기 쪽이 더 작으면(음수 방향) 현재 부등호가 맞다.

**7-2. 점수 함수 보정 (필수)**

FaceLandmarker 는 **얼굴별 신뢰도 스칼라를 결과로 주지 않는다.** 결과에 있는 것은 랜드마크·
블렌드셰이프·변환행렬뿐이다. 그래서 `ai-pipeline.md` §6이 말하는 "신뢰도 θ"를 모델 출력에서
그대로 꺼낼 수 없고, `scoring.ts`가 프레임 특징에서 합성한다.

> 랜드마크의 `visibility` 필드도 못 쓴다 — **실측에서 전 프레임 0이었다.** 값이 실리지 않는다.
> (참고로 PoseLandmarker 는 실제 값을 준다. 코 0.999·어깨 0.994·엉덩이 0.39~0.49.
> 자세 추정을 쓰지 않기로 한 이유는 6-1 과 `ai-pipeline.md` §3 에 있다.)

지금의 합성 규칙은 이렇다.

- 얼굴이 잡혔으면 → 캘리브레이션 대비 크기 적합도로 0.35~1.0. 작을수록 낮다(유령 검출 배제)
- 얼굴이 안 잡혔으면 → 0에서 시작해 "미검출을 믿기 어려운 사정"만큼 올린다
  (저조도 +0.30, 직전까지 고개 숙임으로 추적되던 중이면 +0.25)

**이 계수들은 근거가 없는 초기값이다.** 실측 로그를 보고 정해야 한다. 판단할 재료는
`sweep` 출력의 오경고·미탐·프롬프트 수 세 개다.

각도는 쓰기 전에 `Scorer` 가 두 단계로 정리한다. **검출 여부에는 손대지 않는다** —
얼굴이 잡혔다는 사실은 각도가 이상해도 그대로 재실이다.

| 파라미터 | 값 | 하는 일 |
|---|---|---|
| `maxPlausiblePitchDeg` | 60 | 이 크기를 넘는 pitch 는 자세 추정이 깨진 것으로 보고 **각도만 버린다** |
| `pitchMedianWindow` | 3 | 고개 숙임 판정에 직전 3개의 **중앙값**을 쓴다. 1이면 필터가 꺼진다 |

중앙값을 **인과적으로**(직전 N개) 낸다. 앞뒤를 보는 3점 중앙값이 이상치 제거는 더 깨끗하지만
미래 프레임을 기다려야 해서 라이브에서 500ms 가 밀린다.

이 정리를 `detector.ts` 가 아니라 `Scorer` 에서 하는 이유는 **로그에 원시 각도를 남기기
위해서다.** 하네스가 로그 위에서 판정을 재계산하므로(5절) 필터도 나중에 다시 튜닝할 수
있어야 한다. detector 에서 걸러 버리면 그 순간 튜닝이 불가능해진다.

IMAGE 모드로 옮긴 뒤로는 공개 영상에서 이상치가 관측되지 않지만(pitch 범위 ±13°)
실기기에서 다시 나올 여지를 싸게 막아 둔 것이다.

**7-3. 자체 호스팅 경로 배치 (필수)**

`assets.wasmBasePath`와 `modelAssetPath`를 프론트 정적 자산 경로에 맞춘다.
`npm run vendor`가 `harness/vendor/`에 받아 둔 것을 그대로 옮기면 된다.
CDN 을 쓰지 않는다 — 발표 당일 CDN 이 느리면 그대로 시연이 막힌다.

매칭 대기 화면에서 `controller.init()`을 미리 불러 3.76MB 를 받아 둬야 입장이 안 밀린다.

**7-4. 프롬프트 UI (필수)**

`onShowPrompt` / `onHidePrompt` 콜백만 있고 화면은 없다. "자리에 계신가요?" 버튼 하나면
되지만, 탭하면 반드시 `controller.tapPrompt()`를 불러야 한다.

15초 안에 반응할 수 있어야 한다. 공부 중이라 화면을 안 보고 있을 수 있으므로 소리나 진동을
붙일지는 팀이 정한다(문서에 결정이 없다).

**7-5. 세션 화면 연결 (필수)**

`onServerVerdict`의 `warningCount`·`evicted`·`closedAbsenceSeconds`를 화면에 그린다.
내 경고와 퇴출은 항상 내 호출의 응답에 실리므로 폴링할 필요가 없다(api-spec §0-7).

**7-6. iOS Safari 확인 (필수)**

Safari 18.4 이상에서 실기기 확인. 그 아래에서는 속도가 크게 떨어진다.
rVFC 지원 여부와 `createImageBitmap` 성능이 확인 대상이다.

**7-7. 발열·프레임레이트 실측 (권장)**

6인 영상 수신·송출이 주된 부하이고 추론은 그 위에 얹힌다. 저사양 기기에서 캠이 끊기면
`inferenceHz`를 1로 낮춘다. 경고 임계가 60초라 1Hz 로도 판정에 지장이 없다.

**7-8. 캘리브레이션 재측정 시점 (권장)**

지금은 localStorage 에 한 번 저장하면 계속 쓴다. 조명이 바뀌면 기준이 어긋나는데 그걸
감지하는 장치가 없다. 세션 시작 시 조도가 저장된 값과 크게 다르면 다시 재는 것이 안전하다.

## 8. 검증한 것과 못한 것

마지막 확인: 2026-08-15 (macOS 14 / Node 24.14.0 / npm 11.9.0).

**실제로 돌려서 확인했다**

- `npm install` → `npm run vendor` → `npm run build` → `npm run selftest` 네 단계가
  기록된 순서 그대로 통과한다.
- `npm run vendor` — 모델을 **네트워크에서 새로 받아** 3.76MB(문서 수치와 일치)를 확인했고,
  캐시본과 SHA-256 이 같다. tasks-vision 런타임 복사도 함께 확인.
- `npm run build` — `tsc` 무오류(TypeScript 5.9.3, strict + noUncheckedIndexedAccess).
- `npm run selftest` — **72개 항목 통과.** 전이표, occurredAt 규약(적는 시각과 보내는 시각이
  다르다는 것까지), UNCERTAIN 동결·상한 격하·저조도 상한, 복귀 임계, 프레임 공백 처리,
  새로고침 복구, 서버 60초 규칙 재현, 하네스 대조, **각도 안정화**(크기 게이트와 중앙값 창을
  하나씩 풀어 각각이 실제로 무언가를 막고 있는지 확인하는 형태다 — 8-1 참조),
  **전송 계층의 조용히 사라지는 경로**(번호 발급의 바닥, 처음 보낸 번호의 409 재발급,
  재전송 흡수 409 는 그대로 성공, 401 의 큐 보존·재개, SS-5 경고 전달 — 9-10~9-12).
- `npm run contract` — **실제 서버(포트 8130)에 SS-4 를 쏴서 15개 항목 통과.** 6인 매칭으로
  세션을 열고 이 폴더의 전송 계층이 만드는 요청을 그대로 보냈다. 확인한 것:
  본문 형식(`type`·`clientSeq`·`occurredAt`)을 서버가 그대로 받는다 / 응답이 SS-4 계약 필드를
  전부 가진다 / **과거 시각(t0)을 보내도 받아들이고 서버가 그 간격으로 60초를 계산한다**
  (70초 구간 → `closedAbsenceSeconds=70`, 경고 1회) / 세션 시작 이전 시각은 400
  `VALIDATION_FAILED` / **429 를 받으면 같은 `clientSeq` 로 재전송해 결국 받아들여진다** /
  같은 번호 재전송은 409 `DUPLICATE_ABSENCE_EVENT` 이고 클라이언트가 성공으로 취급한다.
- CLI `score` / `sweep` 을 합성 로그 파일로 끝까지 실행 — 표 출력과 합격 기준 판정까지 나온다.

**헤드리스 크롬 + 가짜 카메라로 확인했다** (`npm run browser-check`, 2026-08-15)

이전 판은 이 아래 것들을 "카메라가 없어서 못 한다"로 접어 두었는데 **그 전제가 틀렸다.**
크롬은 y4m 파일을 웹캠인 것처럼 물려 준다(`--use-file-for-fake-video-capture`). 실제 카메라
없이 getUserMedia → 프레임 취득 → 추론 → 상태기계 → 전송까지 전부 돌았다.

- **모델 로딩과 추론이 된다.** 자체 호스팅한 wasm 경로로 FaceLandmarker 가 뜬다 —
  워커 안에서 **99~143ms**, 메인 스레드에서 **104ms**.
- **2Hz 를 감당한다.** 프레임 간격 실측 **중앙 500ms · p90 506~595ms**(목표 500ms).
  추론 자체는 프레임당 **중앙 6.3ms**(맥 M 계열, 320x240). 예산의 1.3% 다.
- **rVFC 가 실제로 콜백을 준다**(`frame-source.ts`). 20초에 57~62장이 워커로 넘어갔다.
- **Worker 통신이 돈다**(`worker/`) — INIT/READY, FRAME 전달(ImageBitmap 이관), TICK 회신,
  CALIBRATION_DONE 까지 왕복한다. **단, 모듈 워커로는 못 뜬다. 9-4 를 반드시 읽어라.**
- **`sessionStorage` 가 새로고침을 넘긴다.** START 를 하나 보낸 뒤 새로고침하니
  `{"nextSeq":2,"pending":[],"openStartSeq":1}` 이 그대로 남았다. 번호가 1로 되돌아가지
  않는다 — 이 항목이 깨지면 이벤트가 조용히 사라지는 자리였다.
- **캘리브레이션 8초가 실제로 돈다.** 8157ms 수집 후 `TOO_FEW_SAMPLES` 로 끝났는데
  **이것이 정상이다** — 합성 영상에 얼굴이 없어 검출 표본이 0이고, 그 경우 프로필을 만들지
  않는 것이 설계다(`calibration.ts`). 수집 루프와 경고 경로가 함께 확인됐다.
- **상태기계가 실제 프레임으로 전이한다.** OBSERVING → CANDIDATE → PROMPTING → ABSENT_SENT
  가 순서대로 났고 SHOW_PROMPT·HIDE_PROMPT 가 UI 훅으로 나왔다.
- **브라우저가 실제 서버에 SS-4 를 쏜다.** 포트 8160 에 6인 세션을 열고 붙였더니
  `START seq=1 occurredAt=2026-08-15T23:27:19+09:00` 이 200 으로 받아들여졌고 응답
  (`accepted·warningCount·evicted·pointDelta·closedAbsenceSeconds`)이 훅까지 돌아왔다.
  지금까지의 `contract` 는 Node 가 요청을 재현한 것이었고, **브라우저에서 끝까지 도는 것은
  이번이 처음이다.**
- **네트워크 실패 시 같은 번호로 재전송한다.** 일부러 다른 오리진으로 쏴서 CORS 로 막았더니
  `seq=1` 그대로 세 번 재시도했고, 미전송 큐에 `openStartSeq:1` 이 남았다. 계약대로다.

**여전히 확인하지 못한 것 — 헤드리스에서 됐다고 실기기에서 되는 것이 아니다**

- **실제 사람 얼굴로 판정해 본 적이 없다.** 위 확인은 전부 **합성 영상**이다. 얼굴이 없는
  회색 잡음이라 "미검출을 미검출로 본다"까지만 확인됐고, **얼굴이 있는 구간을 얼굴로 보는지는
  한 번도 확인되지 않았다.** `scoring.ts`의 임계값과 계수는 여전히 근거 없는 초기값이고,
  오탐률은 6절 측정으로만 나온다. 여기서 나온 수치를 정확도로 읽으면 안 된다.
  → **일부는 닫혔다.** 공개 CC0 얼굴 영상으로 "얼굴을 얼굴로 본다"와 "캘리브레이션이 실제
  프로필을 만든다"를 확인했다(6-1). 남은 것은 **고개 숙여 필기하는 자세** 하나이고, 그것만은
  공개 데이터셋에 거의 없어 직접 찍어야 한다(6-2). 대본과 읽는 법은 준비돼 있다.
- **실기기 성능.** 위 6.3ms 는 데스크톱 맥 값이다. 저사양 안드로이드에서 2Hz 를 감당하는지,
  발열로 스로틀링이 걸리는지는 그 기기에서만 안다.
- **iOS Safari.** 크롬으로만 돌렸다. rVFC 와 wasm 동작이 사파리에서 같은지 미확인이다.
- **6인 영상과 동시 실행.** LiveKit 이 6명의 영상을 받는 동안 추론이 프레임을 놓치는지.
  이번 확인에는 LiveKit 이 아예 없었다.
- **캘리브레이션이 실제 얼굴 표본을 채우는지.** 루프가 도는 것은 확인했으나 프로필이 실제로
  만들어지는 경로(표본 10개 이상)는 얼굴이 있어야 지난다.

`selftest`가 통과했다는 것은 "판정 로직이 설계 문서대로 돈다"는 뜻이고, `contract`가 통과했다는
것은 "그 판정이 만든 요청을 서버가 받아들인다"는 뜻이고, `browser-check`가 통과했다는 것은
"그 전부가 실제 브라우저에서 한 줄로 이어진다"는 뜻이다. **셋 다 "자리비움을 잘 잡는다"는
뜻이 아니다.** 그것은 6절 측정의 결과물이고, 측정은 사람 얼굴이 있어야 시작된다.

### 8-1. selftest 자체를 어떻게 믿나

**통과하는 테스트와 무언가를 지키는 테스트는 다르다.** 이 selftest 는 파라미터를 하나씩
망가뜨려 실제로 실패하는지 확인하는 방식으로 검증했다. 처음 29개 항목 중 셋이 아무것도
지키지 않고 있었다.

- `uncertainFreezeMs`(3값 논리)를 통째로 지워 UNCERTAIN 을 MISS 로 세게 만들어도 통과했다.
  동결 테스트가 짧은 클립에 이벤트·프롬프트가 없는 것만 봤는데, 프롬프트는 t0+30초에야
  뜨므로 그 클립에서는 동결이 있든 없든 아무 일도 일어나지 않았다.
- `returnFramesToPresent` 를 3 → 1 로 바꿔도(깜빡임 한 장이 자리비움을 닫는다) 통과했다.
- `promptAnswerWindowMs` 를 15초 → 60초로 바꿔도 통과했다.

셋 다 **상태 전이와 전송 시각**을 보도록 고쳐 지금은 잡힌다. 파라미터를 손보면
(6절의 튜닝이 그 일이다) 다음 규칙을 지켜라.

> 새 판정 규칙을 넣거나 임계값을 바꾸면, **그 값을 되돌려 selftest 가 실제로 실패하는지
> 확인하라.** 실패하지 않으면 그 규칙에는 테스트가 없는 것이다.

`npm run sweep` 이 임계값을 흔들어도 결과가 전부 같게 나오면 클립이 그 축을 시험하지 못하고
있다는 신호다 — 파라미터가 아니라 대본을 의심하라.

## 9. 설계 문서와 다르게 구현한 곳

**9-1. "신뢰도"의 출처** — 문서 §6은 검출 신뢰도를 θ_hi/θ_lo 와 비교한다고 적었지만,
FaceLandmarker 결과에는 얼굴별 신뢰도 스칼라가 없다. `scoring.ts`가 프레임 특징에서 점수를
합성하는 것으로 대체했다(7-2 참조). 모델 자체 임계는 0.2 로 낮춰 둔다 — 모델이 먼저 잘라
버리면 UNCERTAIN 구간을 관측할 수 없고, 하네스에서 임계를 다시 올리는 것도 불가능해진다.

**9-2. 복귀 판정이 상태마다 다르다** — 문서는 "1.5초 연속 검출 → 복귀"만 적었다.
이 구현은 프롬프트가 뜨기 전(OBSERVING·CANDIDATE)에는 HIT 한 장이면 즉시 복귀시키고,
프롬프트가 떴거나 START 를 보낸 뒤에만 3프레임을 요구한다. 전자는 사용자에게 보인 것도 서버로
나간 것도 없어 되돌리는 비용이 0이고 미검출 카운터가 "연속"이라는 정의와도 맞는다. 후자에서
한 장에 반응하면 프롬프트가 깜빡이고 START/END 가 5초 간격 제한에 걸린다.

**9-3. t0 는 "지금 이어지는 미검출 구간의 첫 프레임"이다** — 중간에 HIT 가 한 장이라도 끼면
t0 가 그 뒤로 밀린다. 문서는 t0 를 갱신하는 규칙까지 적지 않았다. 이 선택은 자리비움을 짧게
잡는 방향(미탐 쪽)이며, "오탐과 미탐 중 오탐의 비용이 훨씬 크다"는 §6의 맞바꿈과 같은 방향이다.

**9-4. 하네스는 프롬프트 탭을 재현하지 않는다** — 녹화 영상에는 탭이 없다. 즉 재계산은
무응답 경로만 돈다. 확인 프롬프트가 오탐만 걸러내고 정탐은 그대로 통과시킨다는 §5의 주장과
정확히 같은 조건이라 측정의 타당성은 유지된다. 다만 **실사용에서 탭으로 걸러질 오탐은
이 측정에 잡히지 않는다** — 측정값이 실사용보다 보수적(오탐이 많게 나옴)이라는 뜻이다.

**9-5. 화장실 모드에서 미전송 START 를 버린다** — 문서에 없는 처리다. SS-5 는 서버가 열린
구간을 대신 닫는데, 그 시점에 큐에 남아 있던 START 가 뒤늦게 도착하면 PAUSED 구간 안에 짝 없는
자리비움이 열려 복귀 후 10분짜리로 판정된다. `dropPendingStarts()`가 그것만 버리고 END 는
남긴다(짝 없는 END 는 서버가 `closedAbsenceSeconds=null`로 흘려보내 무해하다).

**9-6. 단일스레드 wasm 은 선택이 아니라 기본이었다** — `@mediapipe/tasks-vision@1.0.1`이
배포하는 wasm 은 SIMD 판과 no-SIMD 판 둘뿐이고 멀티스레드 빌드가 없다. §4가 우려한
COOP/COEP 강제는 이 버전에서 애초에 발생하지 않는다.

**9-7. 캘리브레이션의 "16프레임"은 하한이 아니라 기댓값이다** — 문서 §6은 "8초(16프레임)"이라
적었다. 구현은 수집 시간을 8초로 두고(`durationMs: 8000`) 그 사이 **얼굴이 잡힌** 표본이
10개 미만이면 실패로 본다(`minSamples: 10`). 2Hz 로 8초면 16프레임이 들어오지만 그중 몇 장은
검출에 실패하는 것이 정상이라, 16을 하한으로 걸면 정상적인 캘리브레이션이 실패한다.
10 이라는 숫자 자체는 다른 초기값들과 마찬가지로 측정으로 조정할 값이다.

**9-8. 설계 문서의 수치는 전부 코드와 일치한다** — 2026-08-15 대조 결과, §5·§6이 정한
검사 주기 2Hz, 진입 6프레임(3초), 복귀 3프레임(1.5초), 프롬프트 t0+30초, 무응답 15초,
탭 유예 120/240/360초, 3회 미해소 시 안내, 동결 상한 10초(저조도 20초), 캘리브레이션 8초,
서버 규칙 60초·3회가 `config.ts` 에 그대로 있다. 어긋난 항목은 없었다.

**9-9. Worker 는 반드시 클래식이어야 한다 — 모듈 워커로는 뜨지 않는다**

**이 폴더에서 가장 중요한 제약이다.** 3절이 예시로 적어 둔
`new Worker(url, { type: "module" })` 로는 **모델이 절대 로드되지 않는다.** 헤드리스 확인에서
드러났고, 원인이 우리 코드가 아니라 MediaPipe 의 wasm 로딩 방식에 있어 우회가 없다.

기전은 이렇다.

1. MediaPipe 는 wasm 글루(`vision_wasm_internal.js`)를 `importScripts` 로 싣는다.
2. 모듈 워커에서 `importScripts` 는 **정의는 되어 있지만 부르면 TypeError** 다
   (실측: `Module scripts don't support importScripts()`).
3. 라이브러리가 그 TypeError 를 잡아 동적 `import()` 로 대체한다.
4. 그런데 그 글루는 **UMD 클래식 스크립트**다. 최상위 `var ModuleFactory` 가 전역이 되는 것을
   전제로 라이브러리가 `self.ModuleFactory` 를 읽는데, 모듈로 평가되면 그 값이 모듈 스코프에
   갇힌다 → `ModuleFactory not set.`
5. 전역 대입을 억지로 붙여 4번을 넘겨도 그다음이 `custom_dbg is not defined` 다. 글루 전체가
   클래식 스크립트 의미론에 기대고 있어서 한 줄 보정으로 해결되지 않는다.

**해결은 워커를 클래식으로 뽑는 것 하나다.** 클래식 워커에서는 `importScripts` 가 정상
동작하고 글루가 클래식으로 평가된다. 확인된 방법은 번들러로 IIFE 한 덩이를 만드는 것이다.

```bash
npx esbuild dist/src/worker/detector.worker.js \
  --bundle --format=iife --platform=browser --target=es2022 \
  --outfile=dist/worker-classic.js          # 236KB
```

```js
createWorker: () => new Worker("/ai/worker-classic.js"),   // type: "module" 을 주지 않는다
```

Vite·Next 를 쓴다면 각자의 클래식 워커 문법을 쓰면 된다(Vite 는 `?worker&inline` 이 아니라
클래식으로 뽑는 옵션을 확인할 것).

**곁들여 확인한 것 하나 더** — 번들러 없이 `dist` 를 그대로 모듈 워커로 물리면 `dist` 안의
베어 스펙파이어(`@mediapipe/tasks-vision`)를 브라우저가 해석하지 못해 워커가 아예 뜨지 않는다.
그때 화면에 보이는 것은 **"모델 로딩이 30초 안에 끝나지 않았다"** 뿐이다(컨트롤러의 타임아웃).
워커 로딩 실패가 조용히 타임아웃으로 둔갑하는 자리라, 붙일 때 콘솔의 워커 오류를 함께 봐야 한다.

**9-10. `clientSeq` 의 바닥은 저장소가 아니라 세션 경과 초다 (W1)**

문서는 `sessionStorage` 로 번호를 보존한다고 적었다. **그것이 막는 것은 새로고침뿐이다.**
탭을 닫았다 다시 들어가거나, 새 탭에서 열거나, 브라우저가 재시작하거나, iOS 가 메모리 압박으로
탭을 버리면 저장소가 비어 `nextSeq` 가 1 로 되돌아간다. 서버는 `uk_ae` 로 전부 409 를 내는데
옛 클라이언트는 그것을 성공으로 취급했다 — **그 세션의 감지가 통째로 꺼진다.**

두 가지를 겹쳐 막는다.

1. **저장소를 `localStorage` 로 바꿨다.** 탭·재시작을 넘는다. 접근이 막히면(사파리 사생활 보호)
   `sessionStorage` → 메모리 순으로 물러난다.
2. **`sessionStartedAtMs` 를 주면 "세션 경과 초"가 번호의 바닥이 된다.** 저장소가 통째로 비어도
   앞 실행의 번호를 넘어선다. 근거는 5초 페이싱이다 — 앞 저장소가 T0 에 바닥 F0 을 잡았다면
   시각 T 까지 쓸 수 있는 번호는 많아야 `F0 + (T-T0)/5` 인데, 뒤에 만들어진 저장소의 바닥은
   `F0 + (T-T0)` 이라 항상 그보다 크다. 서버 계약은 건드리지 않는다(`clientSeq` 는 `long`).

그래도 겹치면(바닥을 안 넘겼거나 틀렸을 때) **안전망이 하나 더 있다.** 보낸 적 없는 번호에
409 가 오면 그 이벤트는 서버에 없다는 뜻이므로, 번호를 건너뛰어 다시 매기고 재전송한다.
`onUnexpectedDuplicate` 가 그 사실을 알린다 — **정상 동작에서는 불리지 않아야 하는 훅**이다.

"보낸 적 있는 번호인가"는 `PendingEvent.attempts` 로 가른다. 재전송이 흡수된 409 는 계약대로
성공이고(1회 이상 보낸 번호), 처음 보낸 번호의 409 만 재발급 대상이다. `attempts` 를 저장까지
하는 이유는 응답을 못 받고 새로고침된 경우에도 판단이 옳아야 하기 때문이다.

실측(`npm run w1-check`, 실제 서버):

```
[0]  첫 탭            START#1:OK END#2:OK                          경고 1
[A0] 고치기 전        START#1:409 END#2:409                        경고 1 → 1   사라짐
[A]  고친 뒤(바닥 없음) START#1:DUP START#2:DUP START#4:OK END#5:OK  경고 1 → 2   기록됨
[C]  고친 뒤(바닥 있음) START#110:OK END#111:OK                     경고 2 → 3   기록됨
```

**9-11. 401 은 재시도로 풀리지 않는다 — 큐를 붙들고 멈춘다 (W2)**

`FetchAbsenceTransport` 는 429·409·400·403·404 만 분기하고 나머지를 `NETWORK_ERROR` 로 흘렸다.
401 이 거기 걸려 **30초 백오프로 세션이 끝날 때까지 두드리고 아무도 알지 못했다.**
그 사이 자리비움은 하나도 기록되지 않는다. 토큰 만료는 4시간 세션 자체보다 **어제 로그인한
토큰으로 오늘 입장하는 경우**가 현실적이다(유효기간 24시간, 갱신 엔드포인트 없음).

기본값을 이렇게 정했다 — **큐를 버리지 않고, 두드리지도 않고, 멈춘 채 알린다.**

- 버리면 그때까지의 자리비움이 사라진다. 계속 두드리면 지금 버그 그대로다.
- **감지는 계속 돈다.** 멈추면 401 구간의 자리비움을 아예 관측하지 못한다. 이벤트는 큐에 쌓이고
  5초 페이싱상 4시간에도 큐가 터지지 않는다.
- `stopped`(전송 종료, enqueue 도 막힘)와 다른 `paused` 상태다. 멈춘 동안에도 큐는 계속 받는다.

**정책은 앱이 고른다.** `onAuthExpired` 로 알리고 `resumeAfterReauth()` 를 열어 뒀다.
감지를 아예 멈추고 싶으면 훅에서 `dispose()` 를 부르면 되고, 큐를 버리고 싶으면 그대로 두면 된다.
**부르지 않으면 아무것도 나가지 않는다** — 그것이 기본값의 대가다.

**9-12. SS-5 가 낸 경고도 `onServerVerdict` 로 온다 (W6)**

Pause 시작 시 열린 자리비움 구간이 마감되며 경고가 붙을 수 있고, 그 사실은 **SS-5 응답에만**
실린다. `onRestroomStarted()` 가 인자를 받지 않아 그 응답을 통째로 버리는 구조였다.
이제 응답을 넘기면 SS-4 응답 모양으로 옮겨 같은 훅으로 흘린다 — 화면이 경고를 그리는 코드를
두 벌 갖지 않게 하려는 것이다. 퇴출·포인트는 SS-5 에 없는 정보라 채우지 않는다
(SS-5 로는 퇴출이 나지 않는다. 3회째는 화장실 모드 자체가 409 로 막힌다).

**9-13. 아직 고치지 않은 것 — 단말 시계가 앞서면 하지 않은 자리비움에 경고가 붙는다 (W3)**

이 폴더의 다른 문제들과 **방향이 반대다.** 나머지는 전부 "이벤트가 사라져 사용자에게 유리한"
쪽인데 이것만 **없는 자리비움에 경고가 붙는다.** 고치는 데 판단이 필요해 이번에 손대지 않았다.

일어나는 조건을 정확히 적는다.

1. 서버는 `occurredAt` 이 `[세션 시작 −5초, 현재 +5초]` 밖이면 400 이다(허용 오차 5초, 양끝 포함).
2. **단말 시계가 서버보다 5초 이상 앞서면** 보내는 모든 시각이 `현재 +5초` 를 넘어 400 이 된다.
3. `sender.handle()` 의 `INVALID` 분기는 "재전송해도 같은 이유로 거절된다"고 보고 이벤트를 버리며
   `clearOpenStart()` 까지 부른다.
4. **START 는 통과했는데 END 만 거절되면** 서버에 짝 없는 START 가 남는다. 그것은 세션 종료
   시각까지 자리비움으로 정산된다 — 60분 세션에서 57분이 자리비움으로 적힌 실측이 있다.
5. 클라이언트는 열린 구간이 없다고 믿게 되어 새로고침 복구조차 못 쓴다.

전제 자체도 틀렸다 — `occurredAt` 이 **미래라서** 거절된 것이면 시간이 흐르면 유효해진다.
반대로 시계가 앞선 채라면 START 도 전부 400 이라 **감지 모듈 전체가 조용히 무력화된다.**

고칠 방향은 둘이다. 어느 쪽도 "보고 내용을 클라이언트가 바꾼다"는 판단이 들어간다.
**최소한 END 는 버리더라도 `openStartSeq` 는 남겨야 한다** — 그것만으로 5번이 사라진다.

- `occurredAt` 을 허용 범위 안으로 당겨 재전송한다(보고 시각을 클라이언트가 고치는 일이다)
- 버리되 `clearOpenStart()` 는 부르지 않는다(복구 경로를 살린다)

## 10. 절대 넣지 말 것

`ai-pipeline.md` §2의 명시적 배제 목록이다. 나중에 "이것도 되겠는데"가 나올 자리라 여기 적어 둔다.

화면 공유·탭 감시, 감정·집중도 추정, 오디오 감시, 키보드 활동 감시,
**얼굴로 사람을 식별해 대리 착석을 잡는 것**(생체인식정보 처리에 해당하고 서비스의 익명 원칙과
정면으로 충돌한다 — v2 가 아니라 영구 배제 권고다).

오탐 비용이 없고 서버 계약을 전혀 건드리지 않는다.
